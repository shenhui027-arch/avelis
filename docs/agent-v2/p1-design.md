# P1 设计说明：证据发现（R）与证据解释（H）的第一版

ADR 0011 第 12 点的实施补充（2026-10-31）。依据是 E1 的结论：首要瓶颈是**证据发现**（D1→D2 改善最大），
其次是**证据解释**（证据到了模型手上，首要原因仍写成贡献最大的成员）。任务书第 15 节 P1 的范围是：
R、H 的最小版本，各用一个开关控制，完成 E2；本阶段不改报告协议。

## 0. 开关与边界

- 两个开关：`analysis_retrieval`（R）、`analysis_investigation`（H），放在 `config.Settings` 里，默认关闭。
  两个都关时，工具列表、预检、上下文包、提示、核验都与 B0 逐字节一致，由回归测试断言。
- E2 的四个条件 B0、+R、+H、+R+H 跑同一份代码，只切换开关。R 不给 H 臂，H 也不给 R 臂。
- 以下都不动：权限、版本、血缘、只读执行、SQL 校验、证据引用、探索标记、审计、撤权检查、统一预算。
  不新增预算，不新增重试。新工具计入现有类别：find / neighbors / path 是元数据工具，计入 `tool_calls`，
  不计入 `queries`（它们不查源库）。系统预检里的调用照常计数。
- 产品代码不出现评测题或任何行业内容（ADR 0010）。表的业务含义只取自元数据：注释、列名、口径定义。
- 先不替换现有的 search_metrics / search_assets / describe_asset / lineage，等 E2 结果再定。

## 1. R：元数据图（`analysis/retrieval.py`）

**节点**的编号是稳定的：`metric:<编码>`、`asset:<库.表>`、`column:<库.表>.<列>`。

**边**（每条边都带类型、来源、状态）：

| 类型 | 来源 | 信任 |
|---|---|---|
| `lineage` | `lineage_edge`（status=active）的列级血缘 | 已证实 |
| `metric_column` | 已发布口径版本用到的列：base_asset 的表达式、时间列、维度列 | 已证实 |
| `join_key` | `lineage_edge.relation = join_key`（从定义里观察到），以及已批准的 `join_path` | 观察到 / 已批准 |
| `shared_key` | 两张表有同名、规范化后同类型的列，并且该列至少在一侧是键（`is_key`、key_columns 或 unique_keys） | 线索 |
| `shared_value` | 两列的已知取值有交集。第一版只用元数据里已有的取值（口径维度取值缓存），不为找边去扫源库 | 线索 |

`shared_key` 和 `shared_value` 只是**发现线索**：输出里标 `clue: true`。它们不是批准的 JOIN，不能升级成血缘，
也不能当作因果边。跨表比较照常走探索查询的校验，或者分别查询后用计算工具合并。

**工具**（只读，输出有上限，被截断时注明 `truncated` 和省略数）：

- `find(词)`：在可见的口径、资产、列的名称与注释里检索，最多 20 条；
- `neighbors(节点, 关系?, 方向?, 深度≤3)`：沿指定类型的边展开，最多 30 个节点；
- `path(起点, 终点)`：深度 ≤3 的最短路径，最多 3 条。

实现用元数据库的递归查询（PostgreSQL `WITH RECURSIVE`），或者有界的逐层查询；不引入图数据库或向量库。
**权限先行**：只有发起人可读的资产（`access.can_read_asset`）才进入节点集合。无权对象不出现在结果、计数和路径里，
也不泄露它是否存在。

**R 的系统预检**：R 开启时，从口径的 base_asset 及其上游闭包出发调用 neighbors，按下面的顺序取前 k 个参考表
（k ≤ 5，文字预算 ≤ 2,500 字符，超出就截断并注明）：

1. 优先上游闭包以外、经 `join_key` / `shared_key` 连到闭包的表；
2. 然后是闭包内的明细表；
3. 同一层里，连接列多的排在前面；最后按名称排序，保证结果确定。

每张表写进上下文包的内容是：限定名、关联理由（经哪条边、哪些列，是否是线索）、注释、关键列（连接列与日期列）。
这等于由系统自动完成 D2：只给定位与元数据，不查数据、不下结论。

## 2. H：证据解释（`analysis/investigation.py`）

1. **变化的分布特征**（确定性计算，H 开启时写进上下文包，不调用模型）：
   - 自动归因各维度中，前 1 名、前 3 名成员占总变化的比例（集中度）；
   - 成员变化率的离散程度。各成员变化率与总体变化率之差都在阈值内时，记为“成员之间均匀”；
   - 日趋势里，变化是否集中在某个时间点（最大单日跳变占总差额的比例），以及跳变的日期。

   阈值是系统常量，写明含义，不为某道题调整。
2. **核验阶段的修订条件**。同时满足以下三点时，要求修订一轮：
   - 首要原因是成员或因子；
   - 分布特征为“成员之间均匀”；
   - 上下文里存在**事件类证据数据集**，且没有被任何原因或结论引用。事件类证据数据集指：来自口径上游闭包以外的表、
     含日期列的记录型数据集（探索查询或预检产生）。

   修订要求是二选一：用证据检验这个驱动因素，或者把结论改成 `insufficient_evidence` 并写明理由。只要求做过检验，
   不强制改选事件作为原因。修订仍然只有一轮，与现有修订共用同一轮，不新增。
3. **推理提示里的对照示例**：用“反例 → 错在哪 → 正确写法”的格式，只用中性占位（成员甲、记录表乙），
   必须通过业务中立扫描测试。

## 3. 测试与回归

- 两个开关都关：与 B0 的工具清单、上下文包、提示逐字节一致。
- R：
  - 权限过滤：无权表不出现在 find / neighbors / path 的结果、计数和路径里；
  - 深度上限与输出上限，被截断时注明；
  - 线索边带 `clue` 标记，不能当 JOIN 用（探索校验照常拒绝没有依据的 JOIN）；
  - 预检的 k 与文字预算；
  - 结果确定，同样输入的排序相同。
- H：
  - 分布特征的计算（集中、均匀、单日跳变）；
  - 修订条件三项缺一不触发；
  - 修订只有一轮；
  - 对照示例通过 ADR 0010 扫描。
- 新工具计入 `tool_calls`；预算截止的行为不变。

## 4. E2（任务书第 12 节）

- **场景**：从开发集选 16 个场景，含 E1 的 6 个：h10、e01、h07、f02、h09、d02、e02、h05、d06、f01、c02、g01、
  d03、n01、a02、h12。覆盖探索、维度、因子、日历、治理、简单题、反例和安全题。
- **规模**：16 个场景 × 4 个条件 × 2 次 = 128 次。条件顺序用固定种子随机化。每次运行前恢复相同的数据与权限，
  不共享跨题记忆。
- **环境与预算**：私有库 `avelis_e1`；预算沿用 B0 的冻结上限；费用上限 `--cap 20`。
- **判分**：统一用 v2.1.1。
- **冻结**：运行前把 R、H 的变更清单、开关值、代码 sha 写进 manifest；运行中不改代码，也不改评分器。

## 5. 实施中的调整与已知局限

- **参考表排序**（审查时调整，E2 冻结前）：同一层候选很多时，原来只按限定名的字母序排，结果取决于库名，不代表相关性。
  改为依次比较：闭包外 → 不是兄弟派生表（上游和口径闭包的基表不相交）→ 有日期 / 时间列 → 距离 → 连接列数 → 名称。
  预检只展开闭包的直接邻居，k ≤ 12，条目改成紧凑格式（表名、注释、经由的边、最多 3 个日期列、是否兄弟派生），总长不超过 2,500 字符。
  我当时是想到“有的事件记录表会被字母序埋没”才提出这次调整的，但规则本身是通用的，不针对任何场景或表名。
- **线索边限定在同一数据源**（离线冒烟后调整，E2 冻结前）：
  - 离线冒烟：在私有库上，以有权限的用户跑预检，只读元数据。结果是耗时约 1 秒，没有越权表；但参考表被其他数据源里同名键的表占满。
  - 调整：第一版里，共享键与共享取值两类线索边只在同一数据源内成立，用来控制边的数量。
  - **已知局限**：跨数据源的参考表现在发现不了。这是第一版的取舍，不是语义上的限制：ADR 0009 第 6 点允许模型分别查询后再合并。
  - 这次冒烟之后，不再根据评测场景的检索结果调整排序。
- **共享取值**：只用元数据里已有的取值（口径维度取值缓存），不扫源库。缓存为空时没有这类边，这一点在 E2 结果里单独说明。
