## 3. 按任务书第 12 节的解释

- **D1（只给正确范围）**：v2 0→0，人工审定的机制 1→1。D1 消除了 4 次待澄清，也纠正了 d02、h07 丢掉的“线上”筛选，但结果没有改善。
  → 对这 6 题，**范围不是主要瓶颈**；不过 B0 的待澄清会让 1/3 的 D0 运行停下，范围理解仍需改进，只是收益不在这里体现。
- **D2（再给资产定位与元数据）**：v2 0→2，人工审定 1→6，是**最大的改善**。e01（调价表）、d02 / h07（投放、来源渠道）、
  h10（礼盒）都是在知道相关表之后才找到机制。
  → **证据发现是首要瓶颈**，P1 优先做 R（按需检索与关系发现：指标上游闭包以外的经营事件表）。
- **D3（再给原始查询证据）**：v2 2→2，人工审定 6→5，**没有进一步改善**。h09 全部、f02、h10 多数运行里证据已经在上下文中，
  首要原因仍是最大贡献的成员或乘法因子。
  → 剩下的失败**优先查证据解释**：把贡献定位当原因，不检查事件与日历。这是 H（有界调查：区分性证据、反证、贡献≠原因）的依据。
  模型能力是否足够，需要另立固定证据包的模型 / 思考强度对照（任务书第 12 节最后一段），不在 E1 预算内。
- **输出协议**：有 9 次运行找到了机制，却被首要原因关键字、关键数值的口径绑定、单日行引用卡住。这一部分先查评分器
  （关键字的同义写法、探索证据能否作为关键数值），再查报告协议（原因绑定到单日行、派生值不能绑定），是 E3 的对象。

**下一步建议的优先顺序**：
1. 评分器 v2.1：先由协调会话裁定实体同义写法与探索证据关键数值的规则，再对 E1 全部 48 次与历史结果一致重评；
2. R（发现）；
3. H（证据解释）；
4. 报告协议（E3）；
5. 范围理解（丢筛选、同名口径跨域），作为 B0 或 P1 的小修。

R 与 H 需要在 E2 里各自隔离验证。D2 与 D3 的交互（D3 没有在 D2 之上再改善）提示：瓶颈不只一个，不能从单个差值认定唯一根因。

## 4. 运行中发现的 B0 缺陷（未修，记下待定）

1. **传输错误的重试规则没有生效**：LangChain 把超时包成 `OpenAITimeoutError`，`agent.TRANSIENT_ERRORS` 只认 openai 的类名，
   所以 h07 / D3 第 2 次没有按预先定义重试一次。v2 把它判为基础设施失败（不算模型失败）。修复方法是按异常继承关系或同时认包装类名，
   改后需加回归测试；本轮按“运行中不改”的规则没有修。
2. **token 上限只在请求前检查**：e01 / D2 第 2 次在第 16 次请求后累计输入 573,182，超过上限 552,321 约 3.8%。任务书第 13 节说
   “接近上限时动态限制剩余输出”，B0 没有实现预估，单次请求可能越线；这次运行恰好也用满了模型请求次数。
3. 评分器：见第 1.1 节。
