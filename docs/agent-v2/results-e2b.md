# E2b：思考强度“最高”对照（B0 @ max）

结论先说：**“最高”档不值得在产品里用**。通过数和“低”档一样（12 / 32），完成运行的耗时中位从 77 秒变成 278 秒，每次通过的费用是“低”档的 3.3 倍。
产品目标是耗时中位 ≤40 秒，“最高”档的完成运行没有一次做到（最快的一次 99.5 秒）。

## 1. 运行

- **E2b-2**（有效结果）：2026-10-31 15:34–17:26，代码 `071eb5c`，冻结记录见 manifest 的 `e2b_2`。
  - 原始结果：本 worktree 的 `.demo/experiments/e2b2/20261031-153430.json`，摘要在同名 `.summary.json`。
  - 只跑 B0，思考强度 max，16 个场景各 2 次，种子 20261101（和 E2 相同），判分用 v2.1.3。
  - 相对 E2 改了三个上限：每次请求超时 60 → 162 秒，单次运行时长 300 → 488 秒，累计输出 token 30,716 → 54,976。其余上限不变，前提变化写在 manifest 里。
- **对照**：E2 的 B0 @ low（`.demo/experiments/e2/20261031-123611.json` 中 B0 的 32 次）。
  - E2 当时用 v2.1.1 判分；v2.1.3 对这 128 次重判没有任何变化（见 scorer-v2_1.md §6），两组可以直接比较。
- **作废**：E2b 第一版的 5 次不计入结果，见第 5 节。
- **恢复**：运行结束后，私有库 avelis_e1 里分析用途的 reasoning_effort 已核对为 null（原值）。

## 4. 预算用尽与上限

- 最高档有 5 次完成了运行，但模型没在预算内提交报告，产品给出“未下结论”的兜底报告，记为未完成：g01#1、h07#1、h07#2、n01#2、f02#2。低档没有出现这种情况。
  - 限住它们的是 token 上限，不是时长：耗时 256–323 秒，都在 488 秒以内。
    - g01#1、h07 两次：累计输入 token 已经超过 50 万（上限 552,321），下一次请求放不下；
    - f02#2：输出 token 正好到 54,976 的上限；
    - n01#2：输出 token 达到 53,639，接近上限。
  - 也就是说，最高档要想把题做完，输入、输出 token 上限都还要再放宽。那样只会更慢、更贵，所以没有再跑。
- 有 5 次累计输出越过了 54,976 的上限（最多 62,642）。这是已知局限：剩余额度在 8192 以上时，不限制单次输出，最后一次请求可以越过上限。

## 5. 作废的 E2b 第一版（保留记录）

- 2026-10-31 15:03 起，代码 `3cfc90e`，冻结记录见 manifest 的 `e2b`；原始结果在 `.demo/experiments/e2b/20261031-150348.json`。
- 每次请求超时仍是冻结的 60 秒。最高档的请求经常超过这个时长，重试一次后仍然超时，运行就失败了，测不出模型能力。

## 7. 对产品的结论

- **不把“最高”设为默认，也不作为可选的“深度分析”档推荐**：
  - 通过数没有提高；
  - 耗时约是低档的 3.6 倍，远超“中位 ≤40 秒”的目标；
  - 每次通过的费用约是低档的 3.3 倍；
  - 在现有预算下还多出 5 次没能提交报告。
- 模型能力不是当前的瓶颈，下一阶段的投入仍放在证据发现和范围澄清（见 next-phase-plan.md）。
- 低档本身也没达到 40 秒的目标：完成运行的中位是 77 秒。这要靠减少请求次数和上下文长度来解决，与思考强度无关。
