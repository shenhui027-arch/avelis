## 1. 两条规则（协调会话 2026-10-31 批准）

1. **首要原因按机制匹配**。每题写资产（限定名）与成员，依据是生成器的场景常量与视图定义（每项的 why 写在规格里）。
   命中需要同时满足两点：
   - 首要原因的证据数据集来自该资产，或者它的视图血缘上游包含该资产；
   - 证据行里有这些成员。编码与显示名的对应（douyin ↔ 抖音、SW ↔ 西南）取自生成器字典（REGIONS / CITIES / PAID_CHANNELS），
     没有逐题的同义词表。派生值会展开到它聚合的所有输入行，每一行都必须属于这些成员。

   类型、方向、核验要求与 v1 相同。禁止关键字与原因必含也用同一字典展开。
   规格里有两处不再沿用 v1 关键字：f02 的“家电”、e01 的“数码”是题目范围本身，不算机制；h10 / h12 的“礼盒”也不算，
   因为生成器的中秋礼盒季提高的是整个“食品”类目，没有单独提高礼盒。
2. **口径类关键数值可以绑定到探索数据**。数值所在数据集要带探索标记，并满足三个条件：
   - 原值在容差内等于某一期的真值；
   - 实体齐全；
   - 数值列的日期窗口等于这一期（用 sqlglot、starrocks 方言求 WHERE、CASE WHEN 与日期分组）。

   只绑定到单日行的不算整个期间。派生（derive）值仍然不能绑定。

## 3. 与人工审定核对（E1 48 次，未列出的运行按否计）

审定表：`experiments/agent-v2/e1/human_audit.yaml`，在评分器冻结前写定。
- **原审定**（E1 回报时）：假阳性 3、假阴性 2。
  - 3 次假阳性就是原来标“弱”的 d02 / D1#1、h07 / D0#2、h07 / D1#2。复核原始轨迹后确认，它们的证据行来自
    `DATE_TRUNC('MONTH')` 分组，行里的 2026-09-01 / 2026-07-01 是月份，不是单日。**原审定把这三次看错了**，已在更正审定里改为找到机制。
  - 2 次假阴性：h10 / D2#1（礼盒，见上）和 f02 / D2#2。
- **更正审定**：假阳性 0、假阴性 1。这次是 f02 / D2#2“件数变化的贡献”：它是派生值，输入是探索得到的家电两期件数，v2.1 不能把派生值绑定到 `ec_units` 因子。
- 结论：v2.1 与更正审定在 47 / 48 次上一致，没有明显不一致，规则没有再改。

## 4. 已知局限（v2.1 冻结，未修）

1. 跨维度成员“A / B”没有拆开比对，导致 3 次历史假阴性（d06 两次、h01 一次）。修法是按产品的“×”维度把成员拆成各自的成员再比对，属于实现修正。
   要不要出 v2.1.1 并重判，需要协调会话决定。
2. 派生值的首要原因只按被聚合的输入行比对成员；没有口径编码的派生因子（如 f02 / D2#2）不能匹配 `factor` 备选。
3. 探索关键数值不判多出来的筛选（例如 d02 的“线上”），结果里列出 `extra_filters`。探索 SQL 的列没有口径维度映射，
   所以以真值相等加成员齐全作为绑定依据。
4. 成员只比对证据行单元格的值，不核对它在哪一列；本数据集里成员的编码和名称在各维度之间不重名。
