## 3. 执行前核对（修复元数据过期窗口）

**问题**：轮询采集之间，库侧可能已经变了。M4 只验证了“采集前新问题如实报错”；走查发现，采集前的同一问题会命中缓存，返回旧结果。

另一个更隐蔽的情况：视图定义改了但还没采集时，查询会按新定义执行，返回 270，却仍然挂着“实付销售额”的口径。

**做法**：每次执行前（包括命中缓存时），用只读账号读取来源对象当前的列和视图定义，与上次采集比较。

- 只看口径实际依赖的列，沿已解析的血缘一直展开到实体表；无关列的增删不拦截。
- 视图定义一变就拦截。
- 不一致时：不执行、不用缓存（`metadata_stale`）；说明哪个对象哪里变了；为该数据源排队一次采集（已有待办则不重复）。
- 由 `AVELIS_ASK_LIVE_CHECK` 控制，默认开启。

**能力**：这是引擎能力 `live_check`，目前只有 StarRocks 声明了。

**代价**：每次问数多两次 `information_schema` 查询。

**验收**：

- `test_m4::test_06b`：视图改为净额但未采集。同一问题不返回缓存的 300，也不返回 270，而是拦截并排队采集；改回原定义后缓存重新可用。
- `test_m4::test_07`：删列后、采集前，新问题和缓存过的问题都被拦截，只排队一次采集；订单数照常回答；关闭核对时数据库如实报 1064。

## 5. worker 长时间运行

```bash
cd backend
uv run python -m avelis.bootstrap demo --metrics
uv run python ../scripts/worker_soak.py --minutes 60
```

**做法**：

- 两个数据源的采集间隔临时改为 1 分钟，worker 每 20 秒检查一次；
- 第 20 分钟重启 Valkey；
- 第 40 分钟用 root 把 `daily_sales` 改为净额，不手动采集；
- 每分钟记录一次 worker 存活、内存、采集与任务状态。

结束后视图与采集间隔都已恢复。

## 7. 第二种引擎：PostgreSQL

按 ADR 0004 的步骤接入。核心模块没有为 PostgreSQL 加任何分支，只做了两处通用扩展：

- 引擎可以声明“catalog 段取自数据源的哪项配置”（PostgreSQL 取库名）；
- 引擎声明自己需要的连接配置项（`options`），前端据此渲染表单。

- **演示实例**：Compose 新增 `shop-pg`（PostgreSQL 18），库 `storedb.store` 中有门店、销售单、退货单和视图 `city_daily_sales`。基线为 2026-09-15 上海 250.00、北京 80.00。`demo.py seed` 会重建这个模式，基线检查从 8 项增加到 10 项。
- **采集**：采集账号只读系统目录 `pg_catalog`，没有任何表的 SELECT 权限（已实测：查业务表被拒绝）。物理身份用 `pg_class.oid`；会话的 `search_path` 置空，视图定义输出完全限定的表名；实例身份用 `system_identifier` 加库名。
- **能力**：元数据、视图血缘、问数执行、执行前核对。PostgreSQL 不记录表的最近修改时间，所以不报告数据新鲜度，不用统计信息冒充。
- **执行**：只读事务内执行，带 `statement_timeout`。错误按 SQLSTATE 归类：57014 → 超时；42703 / 42P01 → 对象无法解析；42501 / 25006 → 权限。
- **验收**：`test_m7_postgres.py`（7 项），覆盖：
  - 创建数据源时校验必填配置；
  - 采集 4 个资产、视图列级血缘、主键粒度；
  - 问数得到 250.00 / 80.00，SQL 为 PostgreSQL 方言；
  - 粒度核验发现重复（9002）；
  - 改名保留身份，删后重建是新资产；
  - 视图定义改了但未采集时，执行前核对拦截；采集后口径受影响；
  - 超时、列不存在、只读事务写入的如实报错；采集账号读不到业务数据。
