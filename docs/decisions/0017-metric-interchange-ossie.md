# ADR 0017：口径按 Apache Ossie 导入导出，并为口径补充给模型用的语义提示

- 状态：已采纳（2026-11-03）。§3 口径语义提示已实现（迁移 0019，`PUT /api/metrics/{id}/ai-context`）；§1、§2 的 Ossie 导出与导入已实现（`GET /api/interchange/ossie/export`、`POST /api/interchange/ossie/import`），锁定规范提交 `48da55a`（见 §4）。原计划“导入等 0.2.0 正式版后再做”调整为：按锁定提交一并实现，规范升级时按 §4 跟进。
- 发布版本：v1.0.2（v1.0.1 及更早版本不包含）。
- 相关：ADR 0005（问数表达力）、0010（业务中立）、0013（准确来自受治理的元数据）、0014（口径时间与量纲）；参考 Apache Gravitino 语义模型设计（`design-docs/gravitino-semantic-model-design.md`，2026-10-30 版）

## 背景

Avelis 的口径（`metric` / `metric_version`）只能在 Avelis 里创建和使用。企业通常已经在 dbt、Cube、BI 工具或 Gravitino 里维护了一部分指标定义，迁移时只能手工重录；反过来，Avelis 审核通过的口径也没法交给别的工具复用。

Apache Ossie（原 Open Semantic Interchange，OSI）定义了与厂商无关的分析语义模型：数据集、字段、关系、指标，以及给 AI 用的 `ai_context`（说明、同义词、示例）。Gravitino 已按它建模，并采用以下做法：

- 每个版本锁定一个 Ossie 规范提交，升级规范要改代码、补测试，不在每个对象上存规范版本；
- 表达式可按方言分别给出写法，未知方言原样保留，不做翻译；
- 写入前做三层校验（结构 → 模型内部 → 对照目录），任一层失败整体不写；
- 明确不做：源表变化后自动重新校验已存的模型。

另一方面，问数代理目前检索口径只用 `name`、`aliases`、`description`（`ask/agent.py`），没有“什么时候该用 / 不该用这个口径”的提示，也没有示例问法。

## 决定

### 1. 不改口径的内部模型，只做双向映射

`metric_version` 仍是唯一的事实来源（依赖指纹、审核流转、时间与量纲语义都不变）。Ossie 只是交换格式：

| Avelis | Ossie |
| --- | --- |
| 口径所在资产（`base_asset_id`）及其字段 | `datasets[]`，`source` 为三段名 |
| `dimensions`、`time_column`（标记 `dimension.is_time`） | `fields[]` |
| 已批准的 `join_path` | `relationships[]`（`from_columns` / `to_columns`） |
| `expression`（数据源方言） | `metrics[].expression.dialects[]`，方言名用 sqlglot 方言名 |
| `unit`、`time_aggregation`、`data_grain`、`polarity` 等 Ossie 没有的字段 | `custom_extensions[]`，`vendor_name = "avelis"` |
| 新增的语义提示（见 §3） | `ai_context` |

一个业务域导出为一个 Ossie 语义模型文件。按 `0.2.0.dev0` 规范，单个文件没有 `semantic_model` 包装，`version`、`name`、`datasets`、`relationships`、`metrics` 等直接放在根部；指标可以放在根部，也可以挂在某个数据集下，Avelis 导出时统一放在根部。

### 2. 导入只生成草稿，必须走现有审核

- 导入时依次做：结构校验 → 模型内部校验（重名、关系两端、列数一致）→ 对照已采集资产校验（源表、列必须存在，按导入人的业务域权限查找，不暴露看不到的资产）。任一层失败整体不写入，并逐条列出原因。
- 通过后生成 `draft` 口径版本，照常算依赖指纹、走 `pending_review → published`。**导入不能直接发布。**
- 表达式只取与数据源方言一致的那一条写法；没有时尝试用 sqlglot 从 Ossie 规范定义的通用方言 `OSSIE_SQL_2026` 转写，转写结果标为“待人工确认”。Ossie 的 `dialect` 是自由字符串，其他未知方言原样保存、不转写。
- `custom_extensions` 里非 avelis 的内容原样保存，导出时原样带回，保证往返不丢信息。

### 3. 口径语义提示（`ai_context`）

`metric` 增加可选的 `ai_context`：

```text
instructions?: string    什么时候该用 / 不该用，例如“退款不计入，需要含退款请用 gmv_gross”
synonyms?: string[]      与现有 aliases 合并检索
examples?: string[]      典型问法，用于检索与评测
```

- 只影响检索与澄清，不进入编译出的 SQL，也不计入依赖指纹。
- 由口径负责人维护，修改写审计。
- 内容来自用户和口径负责人，产品代码不预置任何业务词（ADR 0010）。
- 字段与 Ossie 的 `ai_context` 对象一致（`instructions` / `synonyms` / `examples`），导出时原样映射；Ossie 也允许 `ai_context` 是一段字符串，导入时把字符串当作 `instructions`。

### 4. 版本锁定

每个 Avelis 版本锁定一个 Ossie 规范提交，写在代码常量和文档里。升级规范需要：改映射、补往返测试、在 CHANGELOG 中写明。

**锁定提交：`48da55a`**（`48da55a07e4e8c3a11a662b14727557f6342536d`，2026-11-01，core-spec 最新；schema 最后一次实质改动为 `a498fce`，2026-10-26）。规范版本字符串仍是 `0.2.0.dev0`（草案，项目 2026 年 7 月进入 Apache 孵化器，仍在活跃变动；仓库已改名 `apache/ossie`，机器可读定义为 `core-spec/ossie-schema.json`）。导出严格按该提交的 schema 原文校验，内置副本不做任何改写。

**2026-11-03 更正**：本 ADR 起草时把 Ossie main 分支的形态（根部 `version` / `name` / `datasets` / `metrics`、方言为自由字符串并定义 `OSSIE_SQL_2026`、数据集作用域指标、`ai_context` 对象）当成了 Gravitino 锁定的 `88e0011`。实际上 `88e0011`（2026-07-31）是 `{version, semantic_model: [ … ]}` 包装、方言为枚举（`ANSI_SQL`、`SNOWFLAKE` 等）的旧格式，两者版本号相同、内容不同。端到端验证时发现导出文件不符合 `88e0011` 的 schema，因此改锁到与本 ADR 描述一致的 `48da55a`。为兼容 Gravitino 等仍按 `88e0011` 导出的工具，导入时识别旧的 `semantic_model` 包装：先按 `88e0011` 的 schema 原文校验，再转成新形态走同样的三层校验，并在导入报告里提示按旧格式读取。

映射细节（参考 Gravitino 的做法）：

- 方言名区分大小写，多个方言的表达式原样保留。
- Ossie 的 `datatype` 词表不从源列类型推断，只在口径上明确声明时才导出。
- 导入校验的错误按原因区分：定义有误（400）、无权限（403）、数据源连不上（502），并逐条列出。
- 与 Gravitino 的差异：Gravitino 明确不在源表变化后重新校验语义模型；Avelis 已有变更检测，源表变化会让导入或导出的口径进入“受影响”并阻止使用，这一点保持不变。

### 5. 实施顺序（2026-11-02 定）

1. 第一项：只做 §3 口径语义提示（数据模型、编辑界面、问数检索与澄清使用它、审计），不依赖 Ossie。
2. Ossie 导入导出排在最后（MCP 服务与治理事件之后）。原计划导入等规范 0.2.0 正式版后再做；实际按锁定的规范提交 `48da55a` 一并实现（见第 6 节与“原待讨论项的决定”）。

以上四项（口径语义提示、MCP 服务、治理事件、Ossie 互通）都在 v1.0.2 发布；v1.0.1 及更早版本不包含这些功能。

### 6. 导出的口径必须能被普通 Ossie 消费方算对（2026-11-03 补）

`custom_extensions` 只用来让 Avelis 自己往返，不能承载影响结果的语义。凡是 Avelis 口径里有、但 Ossie 核心模型表达不了的语义，能等价改写进核心表达式就改写，改写不了就**拒绝导出该口径**并说明原因，不导出一个在其他工具里结果不同的口径：

| 语义 | 处理 |
| --- | --- |
| 固定过滤（无维度、无时间分组） | 用 sqlglot 折进每个聚合：`AGG(x)` → `AGG(CASE WHEN 过滤 THEN x END)`，支持 SUM、AVG、MIN、MAX、COUNT 及其 DISTINCT 与 `COUNT(*)`；其他聚合拒绝 |
| 固定过滤 + 维度或时间分组 | 拒绝：折进聚合后会多出 `WHERE` 本应去掉的空分组 |
| 预聚合关联（`pre_aggregate`） | 拒绝：Ossie 的数据集 `source` 虽可写查询，但目前没有可安全往返的分组数据集约定 |
| 仅用于过滤行的内连接 | 拒绝：目标数据集既未被表达式、维度、时间列或过滤引用，也不在这些引用的关联路径上时，Ossie 核心模型无法表达必须执行该内连接的语义 |
| 跨时间聚合 `last` / `avg` | 拒绝：依赖 Avelis 的时间分桶与后续合成；`sum` 照常导出 |
| 派生口径 | 组成口径行集相同时内联成单个核心表达式；行集不同或无法展开时拒绝（取代 §“原待讨论项”第 2 条里只给组成口径公式的写法，结构化组成信息仍保留在扩展里） |

导出最后还会用导入侧的模型与目录校验（只读）跑一遍结果，导不回 Avelis 的文件直接返回 422 并列出原因。导入时，核心表达式与“扩展里的原表达式 + 过滤按同样规则折叠”等价才沿用扩展；不等价说明被第三方改过，以核心表达式为准并给出警告。

已知局限：上表中被拒绝的口径暂时不能导出，需要时可改成在已过滤或已分组的资产上定义口径后再导出。

## 不做

- 不把 Ossie 当内部存储格式，也不在对象上存规范版本。
- 不导入 dbt、Cube 等厂商的原生格式（可由社区先转成 Ossie）。
- 不做 Ontology（概念与映射），等 Ossie 的 Ontology 规范稳定后另议。
- 不在导入时校验表达式的执行语义；执行前的检查仍由发布校验（`publish_check`）负责。

## 后果

- 好处：口径可以和外部工具互通，是开源项目进企业的入口；`ai_context` 直接提高问数检索与澄清的质量。
- 代价：要维护一份映射和一组往返测试；Ossie 仍在 0.x 阶段，规范变动时需要跟进。
- 风险：导入的表达式可能在方言转写上出错。所以转写结果默认待确认，并且必须经过审核才能发布。

## 原待讨论项的决定（2026-11-03）

1. **导出粒度**：按业务域导出，可选只导出其中部分口径（`metric_ids`）；只含当前用户可见的已发布版本。
2. **派生口径**：`expression` 里给出基于组成口径的公式写法，同时在 `custom_extensions`（`vendor_name = "avelis"`）里保留结构化的组成口径（编码、导出方版本号、表达式）。导入时按编码在本环境找到组成口径并锁定**本环境当前受治理的版本**；导出方版本号只作参考，定义不同时给出提醒，不阻止导入。
3. **`ai_context.examples` 与评测**：首版不作为评测题来源，避免评测集被提示内容污染；以后需要时另行讨论。
