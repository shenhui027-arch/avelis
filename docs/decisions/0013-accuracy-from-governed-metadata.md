# ADR 0013：对话式确认与经验学习

- 状态：提议（用户 2026-10-31 定方向；具体范围与顺序在 E2 结论出来后确定，经用户验收后实施）
- 日期：2026-10-31
- 相关：ADR 0006（列注释以数据库为准）、0008（变更留底）、0009（引用渲染与核验）、0010（业务中立）、0011（按需上下文）、0012（系统组装上下文）

## 背景

用户先后两次给出方向（2026-10-31）：

1. “尽可能在架构上提效，从产品层面提升准确率，可以依赖上游对元数据、数据表字段这些的补充……不建议产品设计上把一切都交给大模型，而忽视了底层设计和基础设施架构的建设。”
2. “大模型可以自己找，但是它应该是和用户对话式确认，而不是自己闷头做，最后给一份结果，用户无法质疑无法补充规则，补充完成后 agent 就自我学习，最后压缩成经验，反馈学习，越来越聪明，我认为价值在这里，而不是要用户提前预设好无穷无尽的元数据和描述……”

本 ADR 的第一稿把准确率押在“管理员预先登记驱动因素和关联”上，被第 2 条否定。如果一切靠预设，确定性规则就能完成问答，模型的价值只剩下改写文字；而且预设永远补不全。

两条要求合起来，含义是：

- **模型负责发现和提问。** 它自己去找相关的表、关联和假设，但找到的东西要拿给用户确认，不能闷头用完再交一份没法质疑的结果。
- **用户随时可以纠正和补充规则。** 计划阶段可以，看到结论以后也可以。
- **系统负责沉淀。** 确认过的、纠正过的内容沉淀成经验，压缩整理后在下次分析时取用。用得越多越准。
- **基础设施要扎实。** 包括经验的存储、权限、留底、检索、压缩和冲突处理，以及数值计算、核验和预算。这就是第 1 条说的“底层设计”。
- **上游元数据有就用，但不是前提。**

证据：

- E1 显示，把相关的表告诉模型（D2）带来的提升最大。在对话里，这一步正好可以由用户确认或补充，而不必预先登记。
- 开源产品的做法：Vanna 把执行成功的查询自动收入训练集，WrenAI 支持在使用中补充 instructions 和 SQL pairs。它们都在用使用过程中的反馈积累知识，只是没有做成受治理的经验库。

## 决定

### 1. 分析改为对话式，设置三个检查点

| 检查点 | 模型做什么 | 用户能做什么 |
|---|---|---|
| 理解 | 给出范围（口径、筛选、窗口）；有歧义时追问（沿用现有的追问机制） | 确认或修改范围 |
| 假设 | 预检之后，列出相关的表、准备使用的关联（键），以及待检验的假设。每一项注明是怎么找到的：上游元数据、已有经验、血缘，还是模型推断出的线索 | 确认、否决或补充（例如“还要看活动表”“这两个编码是同一个渠道”） |
| 结论 | 交出报告草稿（数字仍按引用渲染，ADR 0009） | 质疑某条原因，或补充规则（例如“那周系统故障，数据不全”）。模型在同一次分析里重新检验并修订 |

- 用户可以选择“自动”（只在缺少经验或证据冲突时停下来问）或“每次确认”。默认是“自动”：已有经验能覆盖的就直接用，并在报告里写明用了哪些经验。
- 每一轮交互照常计入预算，检查点之间也照常做撤权检查。
- 定时任务（无人值守）只用已确认的经验；遇到需要确认的地方，就按“未确认”写进报告，不能自己当作已经确认。

实现要点（Codex 评审，2026-10-31）：
- 假设检查点放在预检之后：先发起一次“提议”调用，产出待确认的表、关联和假设，再用 LangGraph 的 `interrupt` / `Command(resume)` 暂停等待用户。恢复的写法沿用 `ask/agent.py` 已有的模式。
  - 不在查询循环中途暂停。
  - 运行增加 `waiting` 状态和恢复接口。恢复时要防止重复恢复，并重新检查权限。
  - 预算、工具状态和数据集编号在暂停时做快照；等待的时间不计入运行时长。
- 第一版里，结论质疑通过“续问运行”实现：新运行关联到原运行，带上已确认的范围、假设，以及用户的质疑或补充。在同一次运行里修订留到第二阶段。
- 第一版对提议来源做保守校验：上游资产项须精确对应预检中的完整表名及其引用；经验项须对应本次召回的具体版本，正文只允许空白差异。不能确定来源的关联、假设或改写内容降为 `inferred`，由用户确认；仅有一个合法引用不足以证明任意正文。模型虚构的引用不进入可执行的检查点引用集合。
- 用户补充和续问文字也保留为已确认的本次输入，供后续运行继续继承；继承内容及其经验版本在再次交给模型前重新核权。经验仍须另行明确保存，输入继承不自动建立长期经验。

### 2. 经验：受治理的学习结果

每次确认、否决、纠正或补充，都整理成结构化的**经验条目**：

- **类型**：表关联（键）、口径的驱动因素、取值别名、业务规则或口径约定、分析方法偏好、否定经验（例如“某表与某口径无关”）。
- **内容与证据**：来自哪次分析的哪一轮、由谁确认、原话是什么。
- **作用域**：个人 → 团队 → 全局。提升到全局要经过管理员审批，沿用现有的审批流程。
- **状态**：置信度、使用次数、最近使用时间、是否被后来的反证推翻。

**本次确认与长期保存分开。** 本次分析中的确认和纠正，只对这次分析生效。系统把它们整理成可以编辑的“经验候选”，用户明确点击保存后才进入经验库。用户认可了报告，不等于报告里每条推断都是对的，所以不会自动收录。

开源做法对照：Vanna 保存的是模型自己判定为成功的调用，WrenAI 也是默认就存。我们改为由用户确认后再保存。

最小数据模型：
- `experience`：编号、所有者、作用域、当前版本、状态（有效 / 已撤销 / 已替代）；
- `experience_version`：编号、所属经验、版本号、类型、内容、引用的资产与口径（含版本）、来源（运行、检查点、原话）、确认人与时间、被哪个版本替代。

报告里记录本次用到的经验版本。

治理规则：

- 经验是元数据库里的受治理对象：有版本，变更留底（ADR 0008），可以撤销。
- 经验**不授予任何权限**。涉及资产的经验，只对看得到这些资产的用户生效，检索时先按权限过滤。
- 某个用户补充的规则，只在他的作用域内生效；要对其他人生效，必须先经过审批提升。
- 经验进入上下文时作为数据呈现，并标明来源，不作为指令。里面有指令性的文字时，按 ADR 0012 的对照示例处理：忽略，并在报告中说明。

### 3. 压缩与反馈学习

- **压缩**：定期整理经验库。合并重复的条目；把同一规则在多个成员上的重复确认归纳到维度层面；发现相互冲突的经验时，交给相关用户或管理员裁决；长期不用或被推翻的经验降低权重。原始的交互记录作为留底保留。
  - 归纳由模型提出，但结果仍是待确认的经验，不会自动生效。
- **检索**：理解和预检阶段，按口径、资产和问题字词检索相关的经验，放进上下文包，并注明来源。第一版用 PostgreSQL 的 `pg_trgm` 加结构化键检索，不引入向量库（ADR 0011）。
- **转为确定性检验**：已确认的“表关联”和“驱动因素”类经验，会在下次预检时由引擎直接执行检验（事件是否发生、和变化集中的成员是否重合、量级多大），不用模型重新发现。这样，学到的知识进入了基础设施，而不是只留在提示词里。
- **反馈**：报告被用户认可或否定的结果，计入相关经验的置信度。

### 4. 来源标注与冲突

报告里每条依据都注明来源：上游元数据（ADR 0006）、已保存的经验、本次分析中用户的确认，或模型推断的线索。来源之间**不设绝对的优先级**，否则过时的注释会压过用户刚刚给出的纠正。

- 来源之间有冲突时，把冲突并列给用户，问他以哪个为准。
- 撤销或替代一条经验时，保留原来的版本。
- 模型推断出、未经确认的线索可以拿去检验，但写进结论时必须标为“未确认”。
- 上游元数据有缺口时，照 ADR 0006 暴露缺口；经验库里确认过的列含义，可以作为“建议回写上游”的清单交给负责人。

### 5. 不变

- 数字仍由确定性引擎计算并按引用渲染（ADR 0009），探索查询的校验、权限、预算、审计都不变。
- 模型的自主发现（`query_sql`、R 的图查询）保留。它的产出是“待确认的提议”，不能直接当作结论。

## 评测

单次评分只看最终报告，衡量不出对话和学习带来的价值，需要增加三类评测：

- **交互模拟**：模拟用户只持有一张“业务知识卡”，上面写的是普通业务人员会知道的事（表的含义、编码的含义、一般的业务常识）。这张卡由不看预埋答案的人或会话编写，不能包含答案。模拟用户只按卡回答，卡上没有的就说不知道。
  - 衡量：首要原因命中、需要几轮确认、用户纠正后能否改对。
- **迁移**：第一题学到的经验，能否在不同问题、不同窗口、不同预埋原因的留出题上用上。用来检验学到的是规则，而不是背下了答案。
- **污染**：给出错误或相互冲突的规则，看系统能否标注出来、发现冲突，并且不让它们扩散到其他用户。

原有的单次评分继续报告，便于和 E1、E2 对比。

## 不做

- 不要求用户预先设好全量的元数据。
- 未经确认的推断不能作为已证实的结论。
- 未经审批的经验不跨用户共享。
- 不微调模型，不引入向量库或图数据库。

## 实施顺序

**第一版（一个 PR）**：打通“确认 → 继续分析 → 保存经验 → 下次召回”这个闭环。
1. 预检之后加一次提议调用，提出相关的表、关联和假设；然后用 `interrupt` 暂停，用户确认、否决或补充后恢复分析。
   - 只有提议里包含没有依据的线索时才停下来问，即“自动”模式。
   - 定时任务不暂停。
2. 结论质疑：对已经完成的报告发起续问运行，带上用户的质疑或补充规则。
3. 个人经验：两张表加一个迁移。从确认和质疑中整理出可编辑的候选，用户明确保存后才入库；可以撤销和替代，并保留留底。
   - 权限沿用 `access.py`，审计沿用 `audit.py`。
   - 召回时，先按当前可见的口径和资产键过滤，再做有界的关键词匹配，结果放进上下文包，并标明来源。
4. 前端：继续用轮询；增加等待卡片和确认表单，经验候选可以编辑后保存，报告注明用到了哪些经验。
5. 测试：
   - 恢复后不重复执行查询；进程重启后预算和数据集编号保持正确；同一次暂停被恢复两次时只生效一次；
   - 撤权和跨用户隔离；撤销后的经验不再被召回；经验文本中的指令性文字不被执行；
   - 保留 `verify.py` 的数字核验和业务中立扫描。

**第二阶段**：
- 经验压缩：合并重复、处理冲突。做法参照 mem0 的“新增 / 更新 / 删除 / 不变”判定，删除改为“作废”；
- 团队与全局作用域，提升需要审批；
- `pg_trgm` 检索；
- “关联 / 驱动因素”类经验转为确定性检验；
- 在同一次运行里修订结论；
- 理解阶段的暂停；
- 交互模拟、迁移和污染三类评测（需要授权模型费用）；
- 按需增强上游元数据导入（dbt、数据目录）。

E2 的结论用来调整第二阶段的顺序：R 的召回决定“模型提议”的质量，H 的效果决定结论质疑前要不要先做分布检查。思考强度对照照原计划进行。
