# ADR 0009：报告数字按引用渲染、自动归因、探索查询与评测集

- 状态：已采纳（用户确认先改造再合并 PR #10，2026-10-30）
- 日期：2026-10-30
- 取代：ADR 0007 第 4 点中“从结论文字里提取数字再比对”的全部规则；第 6 点的“默认关闭”与“自动降级为推断”；第 9 点的验收方式
- 修订：2026-10-30 按 DB-GPT 源码改为结构化片段；按 Codex 设计审查（8 条 P1、13 条 P2、2 条 P3，全部采纳）补充第 0、3 点与量纲、归因、评测规则；用户决定把探索查询并入本次改造（第 6 点）

## 背景

ADR 0007 的核验方式是：模型用自然语言自由书写数字，`verify` 再用正则从中文里提取数字，与引用的数据集比对。

PR #10 开发中，这套规则一天内改了 12 次，经过 5 轮 Codex 复核，每轮都还有新反例：

- 放行：“营收千万元”“十分之一”“营收100 万达标”“每 3 个月饼”。
- 误报：“两期总差额”“（万元）”。

中文数字与日期的写法是开放集合。豁免多了会放行，收紧又会误报正常写法。这是方案本身的问题，补规则补不完。

### 开源与业界做法（2026-10-30 调研）

| 项目 | 做法 |
|---|---|
| GROUND（arXiv 2608.26157） | 模型只写 SQL，数字全部来自执行结果；校验对象是 SQL 是否符合口径、粒度、必需过滤、行级权限 |
| InsightPilot（微软，EMNLP 2023） | 模型只编排分析动作；洞察由确定性的洞察引擎计算，明确是为了避免编造 |
| Databricks Genie | 只有完整复用专家核准的参数化查询的回答才标为 Trusted；用基准问题集持续衡量准确率 |
| ThirdEye、wise-pizza | 自动扫描维度、按贡献排序生成下钻；wise-pizza 把两期变化拆成规模与结构两部分 |
| DB-GPT（2026 源码） | 只读 SQL 工具与 Python 沙箱，每次执行保存为产物（artifact）；报告正文由文字片段和引用片段组成，数字按 artifact_id + 字段路径 + 格式取值，建议目标值标为 proposal；文字里仍出现的阿拉伯数字用正则检查（排除日期） |
| WrenAI（2026 源码） | 模型直接写 SQL，但只能针对语义模型（MDL）；dry-plan 展开关联、注入业务规则、执行列级权限，列名错时返回可用列；确认过的“问题-SQL”存入记忆供召回；回答环节不核验数字 |
| SuperSonic（腾讯音乐） | 模型写语义 SQL（用指标、维度名），多组示例并行生成后投票，再由 Schema、时间、Where、GroupBy 等十余个纠错器转成物理 SQL；结果解读默认关闭 |
| TaskWeaver、Data Interpreter | 代码优先，在沙箱里执行 Python |

共同点是数字只来自执行结果：要么把关放在查询一侧（GROUND、WrenAI、SuperSonic），要么让报告里的数字绑定到执行产物（DB-GPT）。没有一家只靠事后从自由文本里提取数字来核对。DB-GPT 对文字中残留的阿拉伯数字仍用带日期排除的正则检查；我们更严格，文字片段里一律不许出现阿拉伯数字，日期也要写成引用。

## 决定

### 0. 能保证什么、不能保证什么（Codex 设计审查后明确，2026-10-30）

- **核验层保证“数值来源”**：报告里每个事实、计算类数字，都来自本次运行的某个数据集单元格或计算结果，量纲与格式匹配，渲染过程没有拼接或改写。界面状态叫“来源已校验”，不叫“已核实”。
- **核验层不保证句子语义正确**：取错列、错成员、错期间，数字仍有真实来源。这部分靠三件事弥补：
  - 界面在每个数字旁显示来源标签，例如“D5 · 成交额 · 区域=华东 · 本期”；
  - 结构化的原因项（第 4 点）；
  - 评测集（第 5 点）里逐题断言关键数值。
- **能结构化判断的错误一律硬拦截**；只能靠语言理解判断的，交给评测衡量，不再加词表。

### 1. 报告用结构化片段书写，数字由后端渲染

模型提交报告时不写数字，只写引用；后端取值、格式化后生成正文。这参照了 DB-GPT 2026 年报告规格（`ReportPart = str | ReportReference`），不使用内联占位语法，因此不涉及转义，由 pydantic 和工具的 JSON schema 直接校验。

**适用范围**：报告的所有模型字段都写成片段列表，并使用同一套渲染与核验，包括标题、摘要、“未解释”、每条结论正文，以及 premise、validation。

**片段类型**（均为 `extra="forbid"`）：

| 类型 | 字段 | 说明 |
|---|---|---|
| 文字 | 字符串 | 规则见第 2 点 |
| `NumberRef` | `dataset`、`column` 或 `summary`、`match` 或 `row`、`format`、`direction`、`role` | 取数值单元格，见下文 |
| `LabelRef` | `dataset`、`column`、`match` 或 `row` | 取维度列的文本值，例如带数字的店名“广州10号店”；只能取维度列 |
| `CountRef` | `dataset`、`distinct` | 某个维度列的不同值个数，例如“{n} 家门店”。不计 NULL 和空串，按规范化后的字符串比较；截断的数据集不可用；`rows`（结果行数）不能用作业务计数 |
| `WindowRef` | `window`（`run_current` / `run_compare` / `dataset:<D>`）、`format`（`range` / `month`） | `month` 只用于完整的单月，跨月或不足整月时拒绝 |

**`NumberRef` 的规则**：
- `match` 必须恰好选中一行，不做隐式求和（求和请先用 `derive`）。`row` 是从 1 开始的行号，越界拒绝，只用来定位，不代表排名；排名结论要引用明确排过序的结果。
- `summary` 只能取计算工具公开的汇总路径，例如 `summary.value`、`summary.total.change`、`summary.day_count_effect`。每个工具在代码里登记它的路径和量纲。
- 被引用的单元格必须是数值，并且带有**量纲**（见下文）。文本列不能当作数值引用。
- `role`：默认 `fact`；`proposal` 表示建议的目标值，界面标“建议目标（非观测值）”，只能出现在推断、建议类结论中。

**量纲与单位**：数据集的每个数值列都带 `kind` 和 `unit`。

| `kind` | 含义 | 来源 |
|---|---|---|
| `level` | 水平值（成交额、订单数） | 指标值列 |
| `delta` | 差额（本期 − 对比期） | contribution、factor_decompose 等计算工具 |
| `ratio` | 比率水平（客单价、转化率） | 派生指标 a / b |
| `rate_change` | 相对变化率（增长 20%） | 计算工具，或 `derive` 能识别的形式 `a / b - 1` |
| `share` | 占比、贡献占比 | 计算工具 |
| `count` | 计数 | `CountRef`、计数类指标 |
| `unknown` | 无法判断 | `derive` 无法识别的公式 |

- 指标单位来自口径：口径版本新增可选字段 `unit`（例如 元、单、人）和 `unit_scale`（默认 1；列本身已是“万元”时为 10000）。这是新增的治理元数据。缺单位的口径和缺字段注释一样，在治理页面列为待补，倒逼补全。
- 格式只能用在相应的量纲上，并由格式器统一输出单位：

| 格式 | 允许的量纲 | 输出 |
|---|---|---|
| `d0`–`d4`、`int` | 全部 | 数值加口径单位 |
| `wan0`–`wan2`、`yi0`–`yi2` | `level`、`delta`、`count` | 先按 `unit_scale` 换算回基本单位，再除以 1 万 / 1 亿，输出“万元”“万单” |
| `pct0`–`pct2` | `rate_change`、`share` | ×100，带 % |
| `pp0`–`pp2` | `ratio` 类数据集里的“比率差”列 | 个百分点 |
| `x0`–`x2` | `ratio` 类的倍数结果 | 带“倍” |

- `unknown` 量纲只能用 `d*` 和 `int`，不带单位。
- 每个引用只用一个格式，不能叠加；四舍五入统一用 ROUND_HALF_UP。

**变化方向**：`delta`、`rate_change` 类的值可以带 `direction`（`up` / `down`）。
- 带了 `direction`：核对原值的正负，一致则显示绝对值，不一致就判错。
- 没带 `direction`：显示带符号的值（+ / −）。
- 水平值不做方向检查，例如“下降至 X”中的 X。

**渲染结果**：
- 每个字段都保存 `parts`（模型原文）、`text`（渲染后的正文）、`segments`（文字段与数值段，数值段记录来源路径、量纲、格式、原值、显示值）、`status`、`errors`（结构化的错误列表）。
- 页面和导出都读同一份保存结果，不在页面上临时渲染。
- 解析失败时保留原文，并逐个片段标出错误。
- PDF、Markdown 导出正文用 `text`，附录列出数值来源；CSV 另附一张来源表。推断标识和字段级错误在离线导出里也要保留。
- **引用自动得出**：refs 等于显式 refs 与所有引用片段涉及的数据集的并集。

### 2. 核验改为结构检查

不再从正文里提取数字。以下规则适用于事实、计算类结论，以及标题、摘要、“未解释”：

1. **引用必须能解析**：数据集、列或汇总路径存在；恰好选中一行；值是有限数值；量纲允许所用的格式；方向与正负一致。
2. **数值段不能拼接**：两个数值段之间如果只隔着空白或 `. , e E + - ×`，或者直接相邻，判错，防止拼出新数字。数值段后面紧跟的文字不能以单位或数量后缀开头（%、倍、成、元、万、亿、个百分点、折）。单位只能由格式器输出。
3. **文字片段里不能有阿拉伯数字**，半角、全角都算；日期改用 `WindowRef` 或数据集里的日期单元格。
4. **文字片段里不能有中文数量**：
   - 字符集：零〇一二两三四五六七八九十百千万亿，加上财务大写 壹贰叁肆伍陆柒捌玖拾佰仟。
   - 数量词表：倍、翻番、翻倍、成倍、半数、一半、减半、折。
   - 白名单（这些词不算数量），最终版本写在这里，修改必须同步修改本 ADR：一致、统一、之一（前面不是“分”）、一些、一起、一直、一般、一定、一旦、进一步、唯一、单一、一体、一样、一下、一方面、一系列、十分（后面不接“之”）、几乎、万一、一同、一律、一并、一再、一向、一切、同一、一贯、一时、不一、一边、一部分、一方、两者，以及后面跟对比用语的“两期 / 两个时期”。对比用语为：的、之间、之差、之比、相比、对比、差、合计、共、各、均，或者标点、句末。
   - 相对旧规则删除了三项：序号豁免“[第前后] + 中文数字”（“前五家门店”是数量）、“一度”，以及“千万”。
   - 写法被误判时，用修订提示让模型改写，不扩充白名单。
5. **必须有引用**：事实、计算类结论至少引用一个数据集。

**推断、建议类结论，以及 premise、validation**：引用照常渲染；文字片段里允许出现数字（这是假设或方案，不是观测值），界面标为“推断 / 建议，未核实”。

**报告整体状态**分三种：
- 来源全部通过；
- 含未核实的推断；
- 没有可核实的事实。

只有推断、没有事实的报告不显示“全部通过”。评测记录事实覆盖率、推断数，以及修订时把事实改成推断的次数。

**修订**：仍然只给一轮，额外 6 次工具调用，不增加查询额度，也不延长截止时间。反馈逐条写明问题出在哪个字段、哪个片段、什么原因。`found_in` 机制删除。

**ADR 0007 第 4 点中删除的内容**：日期、日历词、名称、对比用语的豁免，数字提取与按精度匹配，“下降”后可对应负值。截断标记、需要全集的计算拒绝截断输入、因子拆解的舍入阈值等规则保持不变。

### 3. 计算工具的约束

- **`derive`**：
  - 公式里的常量只允许 1、100、1000、10000、100000000。其他常量（例如假设的转化率）会把结果标为“假设计算”，只能被推断、建议类结论引用。
  - 每个输入变量都必须真正影响结果：把每个输入各扰动一次，结果不变就拒绝，例如 `a*0+99999`。
  - 结果的量纲由公式形式推断：`a/b` 为 `ratio`，`a/b-1` 为 `rate_change`，`a-b` 为 `delta`，同量纲之间的加减保持原量纲，其余为 `unknown`。
- **上下文证据可引用**：`changes`、`data_health` 产出 `context` 类数据集，有 D 编号。行是固定结构的事件，排序固定，并注明截取范围（每个变更集最多 30 个事件、最近 5 次采集），不能当作完整历史。

### 4. 自动归因工具 `explain_change`

**参数**：
- 指标；
- 本期与对比期，默认取运行窗口；
- 候选维度：可选，默认取该指标允许、且当前用户可见的维度，最多 8 个；显式传入的维度与默认维度走同样的校验；
- 深度：1 或 2；
- `top_k`：每个维度最多返回的成员数，1–20，默认 5。

**适用的指标**（从口径表达式解析）：
- 可加的 `SUM`、`COUNT(*)` 指标，用贡献算法。
- 派生比率 a / b（a、b 都可加），用比率算法。
- `COUNT(DISTINCT)`、`AVG`、`MIN`、`MAX` 等不可加指标：返回“不支持自动归因”和原因，不硬算。
- 无论哪种，成员合计都要和单独查询的总量对账；对不上就拒绝，不能当作舍入差。

**执行契约**：
- 每个子查询前都检查：查询额度、统一截止时间、执行权、当前账号与角色、口径与来源闭包的权限。
- 遇到权限拒绝，按 ADR 0007 处理，例如定时任务暂停，不能当成“这个维度没扫描”。
- 因预算、截止或截断没扫完时，返回 `partial`，写明已扫描和未扫描的维度及原因；排名只在已扫描的范围内成立。
- 深度为 2 时，取第一层排名前 3 的维度两两组合；并列时按维度名排序。

**可加指标的计算**：
- 总差额 ΔT 取自独立的总量查询。
- 成员贡献 c_i 等于该成员的差额。成员取两期并集，新增成员的上期值为 0，退出成员的本期值为 0，并单独标注“新增 / 退出”。
- EP_i = c_i / ΔT，是带符号的净贡献比例，可以超过 100%，不等于覆盖率。

**比率指标的计算**：通过受治理查询分别取各成员的分子 a、分母 b。
- 权重 w = b / Σb，比率 r = a / b。
- 成员贡献：c_i = (w_i1 − w_i0) · r_i0 + w_i1 · (r_i1 − r_i0)，其中第一项是结构效应，第二项是比率效应；交互项归入比率效应。这种拆法不是唯一的，输出时写明。
- 新增、退出的成员单独列出结构效应，不补零也不估算比率。分母为 0 时这一项记为不可计算。
- 输出时“成员比率变化”和“对总体比率的贡献”分成两列，不共用“差额”列。

**变化不明显与相互抵消**：
- |ΔT| 低于阈值（默认为对比期的 1%，可按指标配置），或 |ΔT| / Σ|c_i| < 0.2 时，不生成净变化的原因排名。
- 改为返回“总体变化不明显”或“成员变化相互抵消”，并分别列出增加项和减少项。

**分布变化强度**：
- 用两期成员份额分布之间的 JS 散度表示，只对非负、总量为正的分布计算，否则不计算，也不偷偷取绝对值。
- 它是 Adtributor 的简化变体：维度按分布变化强度排序，维度内的成员按 |EP| 排序，取到累计 EP ≥ 0.67 或达到 `top_k` 为止。
- 输出 `threshold_met` 和实际的累计比例；各维度的 EP 不跨维度相加。
- 0.67 是经验阈值，排序效果以评测为准。

**输出**：一个数据集，记录输入血缘。
- 列：维度、成员、对比期值、本期值、成员变化、贡献、EP、结构效应、比率效应、新增 / 退出。
- summary：总差额、首要维度、累计比例、`threshold_met`、`partial`，以及变化不明显或相互抵消的判定。

**为什么不引入 wise-pizza**：它依赖 lasso 求解和 pandas，我们的数据集规模小。自己实现确定性强，也容易测试。多维组合搜索以后有需要再评估。

### 5. 结构化原因与评测集

**报告新增 `causes`**：一个有序的原因列表，每项包含：
- 类型：成员、因子、日历、治理事件；
- 实体：维度及成员、因子名，或事件的证据 ID；
- 方向；
- 贡献的 `NumberRef`；
- 证据数据集。

**结论类型**：分析结论分三种，`ranked_reasons`（有排序的原因）、`no_material_change`（没有实质变化）、`insufficient_evidence`（证据不足）。前端和导出都按 `causes` 展示“原因排序”。

**评测集**：`backend/tests/eval/analysis_questions.yaml`，不少于 20 题，来自 `ec-truth.json` 中预埋的场景。每题固定以下内容：
- 预期的结论类型；
- 首要原因的实体与方向；
- 关键数值及容差，例如预埋的差额；
- 禁止出现的原因；
- k（由题目固定，不取模型返回的 `top_k`）。

**判分**（确定性，不调用模型）：
- 首要原因：只看 `causes` 的第一项，实体和方向都对才算命中。
- 原因准确率：`causes` 中错误原因所占的比例。
- 关键数值：对应的 `NumberRef` 原值落在容差内。
- 反例题：结论类型必须对，而且不能出现禁止的原因。
- 正文是否提到原因只做辅助的一致性检查，不计分。
- 分母是全部预定的运行，失败或没完成的都算没命中。

**运行器**：`scripts/eval_analysis.py --repeat 2`，结果写到 `.demo/eval/<时间>.json`，并生成 Markdown 汇总。汇总按类别和同一题的重复稳定性分别列出，每题记录：命中情况、来源未通过数、完成情况、工具调用次数、用时、token 数。

**合并门禁**（PR #10 及以后修改分析智能体的 PR）：

| 指标 | 门槛 |
|---|---|
| 完成率 | ≥ 95% |
| 事实与计算类字段的来源未通过数 | 0 |
| 首要原因命中率（正例） | ≥ 80% |
| 反例题 | 编造原因的次数为 0（单独门禁，不和总体平均） |
| 越权、预算失效 | 0（单独门禁） |

门槛是早期的质量基线，调整时修改本 ADR。

**测试分层**：
- **确定性回放**：
  - 用真实模型处理合成数据，录制下来，用假模型回放。
  - 录制内容按字段白名单保存，工具结果和错误消息要检查，不许把生产运行转成回放。
  - 冻结数据夹具、窗口、提示、工具模式和录制版本。
  - 至少固定以下轨迹：首轮通过、修订后通过、修订后仍失败、时间不足跳过修订、复合工具中途预算耗尽、复合工具中途被撤权。
- **治理行为**：每一步都走治理、越权被拒、预算生效、定时任务暂停和通知。这些沿用并补充现有的确定性验收，不靠真实模型来证明。
- **真实模型验收**：保留 07 和 08，断言运行成功、首要原因命中、来源未通过数为 0。只有传输层错误（连接失败、SSL、超时）时测试重跑一次；内容问题不重跑。

**成本**：每轮评测约 40 次分析运行，使用已授权用于验收的 DeepSeek 密钥。

### 6. 探索查询 `query_sql`：模型按血缘与注释直接写 SQL

用户决定（2026-10-30）：探索查询并入这次改造，引用探索数据的结论**标注来源，不降级为推断**。这取代 ADR 0007 第 6 点“默认关闭”和“结论自动降级为推断”两条。参照 WrenAI（模型写 SQL，执行前做 dry-plan，列名写错时返回可用列）与 DB-GPT（只读 SQL 工具，每次执行保存为可引用的产物）。

**开关**：数据源新增 `allow_exploration`，默认开启，管理员可以按数据源关闭。关闭后不提供 `query_sql` 工具。

**工具**：
- `query_sql(datasource, sql, purpose, columns?)`：执行一条探索查询，产出 `explore` 类数据集。
  - `purpose` 写明查询目的，记入步骤。
  - `columns` 可选，声明结果数值列的量纲与单位，界面标为“模型声明”。没声明的数值列，量纲按 `unknown` 处理。
- `sample_values(asset, column, keyword?)`：列出某列最常见的取值，最多 20 个，用于写过滤条件。按同样规则校验、计入探索预算。
- 已有的 `describe_asset`（列、字段注释、粒度）和 `lineage`（上下游及关联键）提供写 SQL 所需的上下文；系统提示要求模型先读注释和关联键，再写 SQL。

**校验**（复用 `ask/compiler.validate_sql` 和各引擎的 `SqlDialect`，并在其上增加以下规则）：
- 只允许一条语句，SELECT 或 WITH … SELECT；不允许 INTO、FOR UPDATE、DML、DDL，CTE 中也不允许。
- 只能引用普通表，所有表都必须是该数据源中**当前用户可见的已采集资产**。CTE 名不算表。不允许表函数（如 `url()`、`file()`、`s3()`、`remote()`、`dblink`），不允许系统库（information_schema、pg_catalog、system、sys、mysql 等）。
- 列必须存在于已采集的列中。写错时返回该表的可用列及字段注释，让模型改正（WrenAI 的做法）。
- 函数使用禁止清单：休眠、读文件、外部连接等，如 sleep、pg_sleep、benchmark、load_file、pg_read_file。
- 行数上限：由系统按方言包一层 LIMIT、TOP 或 FETCH FIRST，取 `max_rows + 1` 行，用来准确标记截断。
- 执行：支持的引擎先 EXPLAIN，再用该数据源的只读账号执行，带查询超时；资源上限与问数相同。
- 只读账号的授权是最后一道边界，校验层不能代替它。

**预算**：每次运行最多 8 次探索查询（可以配置），单独计数，并计入总工具调用次数。每次调用前同样检查截止时间、执行权和当前账号与角色。

**结果与报告**：
- 探索数据集保存 SQL、数据源、用到的资产与资产版本、行数、截断标记。
- 报告可以把它作为事实、计算类结论的来源引用。凡是来源含探索数据的数字，都带“探索查询（未经口径审核）”标记，悬停可以看到 SQL。以探索数据集为输入的计算结果，也继承这个标记（沿输入血缘传递）。
- 报告开头列出数字来源的构成：口径查询、探索查询、计算各有多少个数字。
- 有口径能覆盖的数据时，系统提示要求优先用口径；用了探索查询的，要在 `purpose` 里说明原因。
- “把探索查询转为口径草稿”留到后续，不在本 PR。

**评测**：评测集至少加入 3 道需要探索查询的题，例如门店客流与商圈、楼层的关系，或客流计数器故障造成的数据缺口。判分规则不变。另外加入对抗题：越权访问资产、读系统库、调用表函数、多条语句，断言全部被拒绝。

## 实施顺序

都在 `m8-analysis-agent` 分支上完成，全部做完再审查、合并。

1. 结构化片段、量纲与单位（口径新增 `unit`、`unit_scale` 的迁移）、渲染、核验重写；修改 `derive` 的约束；上下文证据数据集；前端与导出；系统提示与修订提示；删除旧的提取代码和测试。
2. `explain_change` 及单元测试，覆盖本 ADR 列出的所有边界：负总差额、接近 0、相互抵消、新增 / 退出、零分母、不可加指标、部分扫描。加入 ADR 0007 第 5 点的标准流程，第 2 步优先用它。
3. 探索查询：`query_sql`、`sample_values`、数据源开关、校验（7 个引擎各自的方言测试，以及拒绝路径的测试）、来源标记的传递、前端标记与 SQL 展示。
4. 报告 `causes`、评测集（含探索题和对抗题）、运行器、回放轨迹；验收用例按第 5 点的分层调整。
5. 全量验收与评测达标，再经 Codex 复核与最终审查，然后合并。

## 后果

- 数字的来源由构造保证，核验从约 300 行正则变成结构检查和量纲检查；中文写法不再靠穷举。语义正确与否如实交给评测衡量。
- 模型的写作自由度下降：数字必须写成引用，原因必须结构化。DeepSeek 等模型需要通过系统提示和示例学会这种写法，评测集用来衡量效果。
- 口径新增单位元数据，缺单位的口径会在治理页面暴露出来。
- 旧的 `analysis_run`（没有 `parts` 字段）只存在于开发库中，不做兼容，开发库直接重建。
- 归因由引擎先给出排名，模型负责解读和下钻；不可加指标会明确说明不支持，不硬算。
- 模型可以按血缘和注释直接写 SQL，查询口径覆盖不到的数据（如客流）；这类数字始终带“探索查询”标记，治理边界靠资产可见性、SQL 校验和只读账号三层把守。注释缺失会直接影响模型找对数据，再次体现 ADR 0006 的价值。
