# ADR 0022：资产档案页与字段血缘的人话说明

- 状态：已采纳
- 日期：2026-11-13
- 发布版本：v1.0.8（v1.0.7 及更早版本不包含）。
- 相关：ADR 0006（字段含义以数据库注释为准）、0010（业务中立）、0013（对话式确认与经验学习）

## 背景

一张表的信息分散在目录、血缘图、变更记录、导入记录和问数依据里，而且多数以工程形式呈现（表达式、指纹、版本号）。业务用户想回答的是三件事：这张表是什么、谁在用；它在哪、怎么产出、最近改过什么；数据从哪来、每个字段怎么加工。

## 决定

1. **一张表一页**。目录的资产详情页（`/catalog/assets/:id`）默认显示档案：顶部是“从哪些表来 → 这张表 → 被哪些地方用”，下面是在用的口径、最近谁问过、最近结构变化、每个字段怎么来的、它是怎么产出的。原有的字段、粒度、对应原表、版本、定义页签保留在档案之后。
2. **只做聚合，不新增采集**。后端新增 `GET /api/assets/{id}/dossier`，把已有数据按表聚合，并按当前用户的权限裁剪。结构变化沿用 `GET /api/change-events?asset_id=`。没有数据的部分整块不显示，不放占位。
3. **不做手填属性**。
   - 写入方式只从导入的脚本推断（整表覆盖、追加、每次重建），推断不出来就不显示。
   - 分层不建模：显示用户自己的库名。
   - 负责人取表所在业务域的负责人；表本身不另设负责人字段。
   - 一句话说明以数据库表注释为准（ADR 0006）；没有注释时才用下面的说明。
4. **“怎么加工”是一句人话，表达式收起**。新增表 `lineage_note`，每个（表，字段）一条，字段为空表示整张表的一句话说明。
   - 模型起草的是草稿，界面标明“待确认”；业务域负责人或维护者确认或改写后才算确认（未归属业务域的表由维护者角色确认）。
   - 每条说明记录写下时字段的来源与表达式的校验码；血缘变了，说明自动标为需要重新确认，不会继续当作有效说明显示。
   - 没有模型、已关闭向模型发送代码片段、或没有人确认时，只显示来源字段、加工类型和可展开的表达式。
   - 发给模型的只有表名、字段名、注释、来源字段和脱敏后的表达式，不含数据；沿用“解释”用途的模型，不新增用途。
5. **可见范围**。
   - 最近谁问过：能看这张表的人都能看到谁、何时、几次；问题原文只给本人和管理员。
   - 产出脚本的原文只给能维护这张表的人；其他人只看到文件名与写入方式。
   - 上下游里当前用户无权查看的表只显示名称，不可点开。

## 不采用的做法

- **复用个人经验表（ADR 0013）存说明**：经验是个人范围、没有待确认状态，说明需要对所有人可见并由负责人把关。沿用的是它“模型提出、人确认后沉淀”的做法，而不是那张表。
- **把说明放进追加式留底链**：说明是可改写的展示文本，不参与问数与口径判断；改动记入审计即可。
- **表上加更新周期、分层等下拉字段**：手填属性会过期，且与实际脚本不一致时没有人发现。

## 后果

- “最近谁问过”在近 30 天的回答与分析数据集上按表筛选，记录量很大时会变慢；到那时再加按表的索引表。
- 先清空再写入的识别依赖同一个导入文件里能看到清空语句；写入方式说的是脚本自己的写法：跨文件的清空识别不到，按分区覆盖或按条件删除后再写的不显示。
- 字段说明不自动随血缘变化重写，需要负责人在档案页重新生成或确认。
