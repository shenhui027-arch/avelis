# ADR 0011：生产规模下的按需上下文

- 状态：已采纳（用户确认，2026-10-30）；在 PR #10 合并后作为下一个里程碑实施
- 日期：2026-10-30
- 相关：ADR 0007（分析智能体）、ADR 0009（引用渲染、探索查询；方言路由已并入其第 6 点）

## 背景

用户要求：业务域很多、表达到几千张时，每个问题不能把整体结构交给模型，而应通过工具取得需要的那一部分，再放进上下文；这是产品能否达到生产要求的条件。

2026-10-30 对 `m8-analysis-agent` 的审计：血缘本来就按需获取（`lineage`、`describe_asset` 都是工具），但以下几处在大规模下会撑爆上下文或变慢。

| 位置 | 现状 | 规模问题 |
|---|---|---|
| `search_metrics`（问数与分析） | 不带关键字时返回全部口径；子串匹配 | 口径一多就撑爆上下文；同义说法搜不到 |
| `search_assets` | 逐表判断权限、逐表查列；按字母顺序取前 40 个 | 慢；前 40 个不是最相关的 |
| `lineage` | 只返回直接相连的一层 | 追溯多层要反复调用；不能只看某一列 |
| `describe_asset` | 返回全部列 | 几百列的宽表挤占上下文 |
| 维度取值匹配 | 取到上限后在本地子串比对 | 高基数维度超出上限的取值匹配不到 |
| 运行预算 | 只限工具调用次数与时长 | 上下文膨胀不受控 |

## 决定

原则：**模型只看到与当前问题相关、经过排序和截断的上下文；任何工具输出都有大小上限，被截断时明确告诉模型如何缩小范围。** 不引入向量库等新基础设施，第一版用元数据库（PostgreSQL）自身能力。

1. **检索**：口径、资产、列的检索都在元数据库中完成，并按权限过滤（集合查询，不逐个对象判断），按名称、别名、注释的相似度（`pg_trgm`）排序，返回前 k 个（默认 10，最多 30），支持分页。不带关键字时只返回业务域与数量概览，不返回全量清单。
2. **血缘子树**：`lineage(asset, column?, direction=up|down, depth≤3, max_nodes=50)`。可以只看某一列，节点超过上限时返回截断标记和“请指定列或缩小深度”的提示。
3. **宽表**：`describe_asset(asset, keyword?, page?)` 按关键字筛选列并分页，默认最多 50 列，先返回有注释、在口径或血缘中出现过的列。
4. **维度取值**：低基数维度在采集时建取值字典；高基数维度改为按关键字实时检索（与 `sample_values` 同一套守卫）。问数理解从“取全部取值再比对”改为“按原话中的片段检索”。
5. **上下文预算**：每次运行按 token 设预算并记录用量；每个工具的输出按 token 设上限。超出预算时与现有预算相同处理：停止并基于已有证据出报告。
6. **工具按阶段开放**：计划阶段只开放检索与上下文工具，执行阶段再开放查询与计算工具，缩短提示，方便本地部署的较弱模型。
7. **大表保护**：探索查询读取的表若采集到的行数超过阈值（可配置），必须带时间或分区列上的过滤，否则拒绝并提示。
8. **模型调用可靠性**：按错误类型重试（连接、SSL、超时），可配置备用模型；失败与重试计入运行记录。
9. **规模验证**：新增一份只含元数据的合成目录（几千张表、几百个口径、多个业务域，含非电商行业的命名），用来测：检索耗时、每次运行的上下文 token 数、评测题在大目录下的命中率是否下降。这些指标进入合并门禁，同时检验产品没有对演示数据集过拟合。

10. **响应时间**（用户 2026-10-30 提出“为什么这么慢”）。实测（`.demo/eval/20261030-192729.json`，52 次分析运行）：单次分析中位 106 秒，其中工具执行（查库、计算）合计中位只有 9.4 秒，其余约 95 秒是模型推理与往返；每次运行中位 24 个步骤，相邻步骤的间隔中位 1.5 秒、P90 12.3 秒，慢的就是那些需要模型重新思考的轮次。做法：
    - **减少模型轮次**：对“为什么变化”这类问题，把变更检查（`changes`）、数据健康（`data_health`）、`explain_change`、日历折算合成一次确定性的“归因预检”，结果一次交给模型，而不是由模型逐个调用；
    - **并行工具调用**：允许模型在一轮里发出多个互不依赖的工具调用，后端并发执行；
    - **前缀缓存**：系统提示与工具定义保持稳定、动态内容放在末尾，利用模型服务的上下文缓存降低首字延迟与费用；
    - **缩小上下文**：第 1–5 点同时缩短每轮输入，直接减少推理时间；
    - 记录每轮的 token 数与耗时，作为规模验证（第 9 点）的指标，并设目标：常见“为什么变化”问题中位 ≤ 40 秒。
    - 问数（单次问答）与分析（多步）分开衡量；评测运行器可以并发执行多题，只为缩短验证时间，不影响产品行为。

11. **探索查询改为结构化描述，由系统生成 SQL**（用户 2026-10-30 提议：方言和 SQL 结构靠工具约束，而不是靠提示词约束）：
    - 把 `query_sql`（模型写 SQL，系统解析、校验、改写）换成 `query_table`：模型提交 JSON 描述，包括主表、关联（只能沿血缘里观测到的关联键，或者右表的唯一键 / 粒度，防止一对多关联放大数字）、列与聚合（枚举：求和、计数、去重计数、平均、最大、最小、条件计数）、过滤（枚举运算符）、分组、时间截断、排序、行数。系统用 sqlglot 的构造接口生成 AST，再按资产所在引擎生成方言。
    - 参照问数的 `query_metric`（已经是结构化意图加编译器），尽量复用其关联与生成逻辑；Cube 的 JSON 查询接口、SuperSonic 的语义解析层是同类做法。
    - 收益：方言问题与自由 SQL 解析带来的整类绕过（PR #10 中 Codex 共发现十余条）从结构上消失，校验器大幅简化；错误能精确定位到字段。代价：没有嵌套子查询、CTE、复杂 CASE，更复杂的分析拆成“多次查询 + 计算工具”。
    - PR #10 合并时保留按 postgres 源方言解析的 `query_sql`（已经过审查和真实引擎验证）；本项是下一个里程碑的第一项，完成后删除 `query_sql` 与其解析校验器，防回流的 sqlglot 用法检查保留。

## 不做

- 向量检索、外部搜索引擎：第一版不引入，`pg_trgm` 不够时再评估。
- 跨数据源 JOIN：不支持；跨源比较由模型分别查询后用计算工具合并（ADR 0009 第 6 点）。

## 实施

PR #10 合并后单独开分支实施。顺序：规模验证数据（第 9 点）先行，用它测出现状基线；再做第 1–4 点；最后第 5–8 点。每一项都以规模验证的指标判断是否有效，不为评测题单独调整。
