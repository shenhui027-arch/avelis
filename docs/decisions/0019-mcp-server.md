# ADR 0019：MCP 服务，向外部 AI 工具提供受治理的口径与血缘

- 状态：草稿（2026-11-01，待讨论）
- 相关：ADR 0005（问数表达力）、0008（审计）、0013（准确来自受治理的元数据）、0017（口径语义提示）；参考 Apache Gravitino `mcp-server/`（独立的 Python 服务，工具按对象分组，每次调用记审计）

## 背景

越来越多的人在 Claude、Cursor、ChatGPT 这类工具里直接问数据问题。这些工具自己写 SQL，不知道企业的口径、关联路径和血缘，答案常常“看起来对”。Avelis 已经有受治理的口径、编译器和血缘，但只能通过 Avelis 自己的页面使用。

MCP（Model Context Protocol）是这类工具接入外部能力的通用协议。Gravitino 用一个独立的 Python 服务，把元数据操作暴露成 MCP 工具，并对每次调用记审计、从认证信息解析调用人。

## 决定

### 1. 形态

- 作为后端的一个可选模块，挂在 `/mcp`，使用 Streamable HTTP 传输。同一个镜像，配置开关默认关闭。
- 复用现有登录和权限：调用方使用个人访问令牌（新增，可吊销、可设有效期，只存哈希）。所有工具按令牌所属用户的业务域权限执行，**和他在页面上能看到、能做的完全一致**。

### 2. 首批工具：只读 + 受治理的问数

| 工具 | 作用 |
| --- | --- |
| `search_metrics` | 按关键词、同义词、业务域检索已发布口径，返回名称、说明、维度、`ai_context`（ADR 0017） |
| `get_metric` | 一个口径的完整定义：表达式、时间语义、单位、可用维度、依赖资产 |
| `ask_metric` | 结构化问数：口径 + 维度 + 时间范围 + 过滤。由 Avelis 编译和执行，返回数字和依据（口径版本、SQL、数据时间） |
| `lineage_neighbors` | 一个资产或列的上下游 |
| `list_changes` | 某资产或口径近期的结构变化和影响 |

- **调用方不能传 SQL。** `ask_metric` 只接受结构化意图，和页面问数走同一个编译器。模型永远不直接写查询，这一点和现在一致。
- 口径状态不是 `published`（例如 `affected`）时拒绝查询，并说明原因，和页面行为一致。
- 结果行数和超时沿用问数的限制。数据发往外部模型的开关（数据外发设置）同样生效：关闭时只返回口径定义，不返回数据行。

### 3. 审计

每次工具调用写一条审计：`action = mcp.<工具名>`，记录调用人、令牌 ID（不是令牌本身）、参数摘要，不记录返回的数据行。

### 4. 写操作暂不开放

创建或修改口径、批准关联路径、导入血缘都不提供。以后如果开放，只能生成草稿或候选，走现有审核，并在工具元数据里标明是写操作。

## 不做

- 不提供执行任意 SQL 的工具，包括只读 SQL。
- 不做独立部署的 MCP 进程，避免出现第二套权限实现。
- 不支持匿名访问。

## 后果

- 好处：外部 AI 工具可以直接用上受治理的口径，答案有依据、可追溯；对开源项目是低成本、高曝光的接入点。
- 代价：新增个人访问令牌（表、页面、吊销）、MCP 模块和依赖（官方 Python SDK，按 ADR 0002 的选型原则记录版本）。
- 风险：令牌泄露等同于账号能力泄露。对策是令牌可设有效期、按业务域限权、可随时吊销，异常调用量进入 ADR 0018 的告警事件。

## 待讨论

1. 个人访问令牌是否允许缩小权限范围（例如只读、只限某些业务域）？
2. `ask_metric` 返回的数据行数上限是否要比页面更低？
3. 是否同时提供 `ask_analysis`（多步分析）？它耗时长、成本高，可能需要异步和配额。
