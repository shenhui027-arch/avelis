# ADR 0021：筛选取值对齐：成员值与业务维表

- 状态：已采纳
- 日期：2026-11-04
- 发布版本：v1.0.5（v1.0.4 及更早版本不包含）。
- 相关：ADR 0010（业务中立）、0012（系统组装上下文）、0013（对话式确认）

## 背景

用户说出的筛选取值可能与数据成员不同。直接把模型理解的原话写入 SQL，会把可识别的范围变成空结果；仅拒绝不存在的取值，也无法利用业务方已经维护的维表。问数与分析需要使用同一套确定性规则，并向用户说明最终采用的范围。

## 决定

产品不管理同义词，不内置地理区划、渠道等业务知识，不新增同义词表或迁移。别名由业务方在自己的维表中维护，通过已登记、已生效的关联路径纳入治理。模型不能自行创造映射，历史经验也不能替代受治理的维表关系。

每个维度的每个取值依次经过以下检查：

1. 与成员值精确相等时保留。
2. 使用 Unicode NFKC、去除全部空白、casefold 进行通用规范化。仅有一个匹配成员时采用该成员，并记录原值与采用值。
3. 按当前口径版本的维度列解析资产与列；派生口径沿锁定的组成口径解析。只使用 `effectively_approved` 判定已生效的单列关联路径：当前列必须是该侧唯一关联列，另一侧必须由 `n1` / `11`（反向为 `1n` / `11`）保证键唯一。另一侧资产是候选维表，另一侧关联列是维表键。
4. 在已采集类型属于文本的维表列中，查找与用户原值相等的行；键列为文本时也参与匹配。查询返回不同键，最多读取三个。唯一键可以采用，多个键只能交给用户选择。说明包含维表限定名和命中列。不同路径、组成口径或所选口径的映射冲突时，需要澄清。
5. 仍未解决时，提供与原值互相包含的成员候选，最多十个；没有包含候选时提供最多十个成员样本。包含只是候选依据，不能自动改写筛选值。没有可用维表路径时提示业务方在维表维护别名并建立关联路径。

维表及其完整来源闭包必须对当前用户可见。维表查询使用 sqlglot 构造字面量和标识符，执行 `validate_sql` 的表、列白名单检查，并使用只读连接、超时、内存及行数限制；读取前核对依赖和库侧结构，防止对齐成为数据权限或治理检查的旁路。

## 不完整样本与失败

成员样本上限沿用 `DIMENSION_VALUES_LIMIT`。样本达到上限时，原值不在样本中不能证明其不存在，必须调用现有精确存在性核验。规范化只在可见样本中进行；维表查询仍照常执行。

守卫或查询失败时，该值是“未知”，保持原值并记录原因，交给后续治理及正式查询处理。未知不等于未解决，也不能被改写成“不存在”。多个口径只有全部确认相同映射才采用；任一口径未知时不能据其余口径擅自改写。

## 接入与可追溯性

共用入口为 `align_filters(session, user, version, filters, settings)`。返回对齐后的 `filters`、逐条 `explanations`、`unresolved` 和 `unknown`。

- `explanations`：`dimension`、`original`、`value`、`method`，方法为 `exact`、`normalized` 或 `dimension_table`；维表方法另带 `table` 与 `column`。
- `unresolved`：`dimension`、`original`、`candidates`、`has_dimension_table`。
- `unknown`：`dimension`、`original`、`reason`。

分析入口在非 chart 范围确定后、lookup 或 precheck 前对齐。多口径仅允许共有维度。非 chart 续问继续沿用已确认范围，并重新核对其筛选取值；chart 续问沿用原数据集。未解决时使用既有 `request_clarification` 流程，记录 `options` 与 `dimension` 供前端展示候选；无人值守任务沿用既有澄清终止流程，不暂停等待。

问数入口在 `submit_intent` 中对齐，可确认的值直接写入 Intent；只有未解决或冲突的取值才返回带候选的错误，由模型调用 `ask_user`。`DemoIntentModel` 和 `match_dimension_values` 的行为保持原样。

采用说明记入运行步骤和答案 / 报告的 `evidence.filter_alignment`；未知记为 `filter_alignment_unknown`。API 同时提供有类型的顶层 `filter_alignment` 列表，便于前端直接展示原话和实际筛选值。既有证据和澄清记录使用 JSON 扩展字段，无需新增数据表。

## 取舍

没有选择产品同义词配置或内置业务字典，因为业务别名属于业务方的数据治理责任，换一个场景就可能失效。没有自动采用子串、编辑距离或模型猜测，因为文字相近不证明业务等价；这类结果只能帮助用户确认候选。

通用规范化仍可能合并业务方有意区分的写法，因此精确匹配优先、规范化须唯一并留痕。维表对齐增加有界的只读查询开销，换来受治理、可核权、可解释的映射；不扫描未经审批、非单列或不能保证维表键唯一的关联。
