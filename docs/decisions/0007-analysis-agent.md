# ADR 0007：分析智能体——模型负责多步思考，治理守住每个数的来源

- 状态：已采纳（M8；用户确认，2026-10-29）
- 日期：2026-10-29

## 背景

用户希望 Avelis 能回答需要多步分析的问题，例如：

- “店铺营业额和店铺位置、人流量是什么关系？该往哪里投流？”
- “为什么上个月和这个月某个指标差这么多？”

用户的判断是：Avelis 的智能必须更多，才能达到开发目标。

### 现状（按 M6 代码核对）

- 问数图是“理解 → 追问 → 治理执行 → 解释”四步（`ask/agent.py`）。每个问题只提交**一次**结构化意图。
- 模型只有四个工具：搜索指标、匹配维度取值、提交意图、追问。
  - 模型看不到血缘、字段注释、变更记录与数据完整性。
  - 不能根据中间结果决定下一步查询。
  - 没有任何计算工具。
- 查询结果默认不发给模型（`modelcfg.DEFAULT_POLICY = {"send_results": False, "send_code": False}`），只能用模板解释。

### 用户决定（2026-10-29）

- **模型可以读取数据与查询结果。** 有保密需求的用户应接入本地模型，而不是由产品限制。
- **治理管“数从哪来”，不限制“想什么”。** 预设口径的作用是保证数字可信，不应成为模型思考的边界。

## 目标与非目标

**目标**

- 模型可以规划并执行多步分析：先看全貌，再按维度、因子下钻，根据中间结果调整方向。
- 分析中出现的**每一个数字都可追溯**：
  - 来自受治理查询（口径版本 + SQL + 结果集）；
  - 或来自后端的确定性计算（引用输入数据集）。

  模型不心算，也不编数。
- 利用 Avelis 独有的上下文：
  - 血缘；
  - 字段注释；
  - 变更记录、受影响与恢复；
  - 采集批次与数据新鲜度。

  “为什么变了”首先回答“是不是口径或数据本身变了”。
- 结论分清**事实、计算、推断、建议**四类，推断和建议都写明前提。

**非目标**

- 不让模型直接对生产库写自由 SQL 并当作可信答案。探索查询见第 6 点，明确标为“未治理”。
- 不做因果推断的自动结论。相关关系只作为线索，建议附验证方式，例如小范围 A/B 投放。
- 不替用户做投放等决策：只给依据与备选方案。

## 决定

### 1. 两种模式，共用一套治理

| | 问答（现有，M6） | 分析（新增，M8） |
|---|---|---|
| 适用 | “9 月 15 日华东实付销售额” | “为什么”“什么关系”“该怎么做” |
| 查询次数 | 1 次（组合问题展开为子查询） | 多次，由模型按中间结果决定 |
| 输出 | 一张结果表 + 解释 | 分析报告：结论、证据链、图表、建议 |
| 用时 | 秒级 | 数十秒到数分钟，后台运行，逐步展示进度 |

路由规则：
- 问答图的理解节点新增“转为分析”的出口：模型判断问题需要多步分析时，返回建议，由用户确认。
- 用户也可以直接选择“分析”。

### 2. 分析图（LangGraph）

```
计划 plan ──▶ 执行 act（工具循环，带预算）──▶ 综合 synthesize ──▶ 核验 verify ──▶ 报告
   ▲              │ 需要用户补充（interrupt）
   └──── 修订 ◀───┘ 中间结果推翻假设时回到计划
```

- **计划**：模型先写出分析计划（假设清单 + 准备做的查询与计算），展示给用户。
- **执行**：ReAct 式工具循环。每一步记录工具、参数、产出的数据集，以及模型给出的理由。
- **预算**（可配置）：
  - 工具调用不超过 30 次；
  - 受治理查询不超过 12 次；
  - 总时长不超过 5 分钟。

  超出时停止，并基于已有证据出报告，同时注明“未完成的部分”。

  实施细节（审计后定稿）：每次工具调用在统一分发层、参数校验之前计数（未知工具、参数无效、重复提交计划都算，只有最终的 `submit_report` 例外）；计划、执行、修订与宽限共用同一个截止时间，每次请求模型前检查，并按剩余时间设置请求超时与重试，截止后不再请求模型。
- **授权**：开始时核对发起人账号存在、启用且有查询角色；之后每次工具调用都重新核对账号与角色（授权前让会话中的用户、口径、资产对象过期）。涉及对象的工具只针对请求的口径与来源闭包核对，规则与口径目录相同，不重建全量目录；来源闭包与问数同一套函数（主表、关联的右表及其上游）。不可见的口径、来源、资产都记为明确的权限拒绝。账号停用或失去角色后，之后的工具调用一律拒绝，不再请求模型，运行记为失败并在报告中写明。
- **运行与后台任务**：
  - 每次运行都经过 Job：异步由 worker 领取；`wait=true` 与任务“立即运行”在请求进程内领取并执行同一个 Job，进程中断时恢复器一样能回收。
  - 执行权是 Job 的本次尝试（`job_id:attempts`）：领取时 Job 仍由本次尝试持有、运行仍在排队才条件更新为 running；每一步提交前在行锁下核对执行权；终态写入再核对一次。失去执行权的执行者不能复活或改写运行。
  - 运行、Job（以及定时任务的暂停与通知）的终态在同一事务提交；Job 的终态跟随分析结果（失败为 failed，暂停或跳过为 skipped）。
  - 恢复器判定 Job 放弃时：运行未结束则终结并补发任务的失败通知；运行已是终态则按运行的终态修正 Job（已因权限暂停的保留 paused），缺少的任务通知补发一次。
  - 加锁顺序全局一致：Job → 运行 → 任务；worker 每一项定时扫描单独容错，失败只记录日志，不退出主循环。
  - 同步入口的 Job 若被扫描 worker 抢先领取，等它到终态（最长 420 秒）再返回。
- 状态沿用 `avelis_agent` 模式下的 PostgreSQL checkpointer。可以中断后继续，也可以追问。

### 3. 工具

**上下文工具**（只读元数据，按用户可见范围过滤）：

| 工具 | 返回 |
|---|---|
| `search_metrics` / `describe_metric` | 口径定义、维度、组成指标、版本历史、当前状态 |
| `search_assets` / `describe_asset` | 资产与列；**字段注释状态**（ADR 0006）；粒度；按名称与注释检索 |
| `lineage` | 列级上下游，以及关系类型（取值、聚合、过滤、关联键） |
| `changes` | 某个时间窗口内，指标、资产的变更事件、版本切换、受影响与恢复、复核结论 |
| `data_health` | 采集批次、数据新鲜度、迟到数据与完整性提示 |

**受治理查询**：
- `query_metric(intent)` 复用 `ask/service.fulfil` 与 `_fulfil_plan`，权限、执行前核对、只读执行、缓存全部不变。
- 每次调用产生一个**数据集**（`analysis_dataset`：SQL、口径版本、结果行、行数上限），用编号引用。

**计算工具**（后端确定性代码，输入为数据集编号，输出新的数据集）：

| 工具 | 用途 |
|---|---|
| `contribution` | 两期差额按维度拆解：各成员的贡献、占比、排序 |
| `factor_decompose` | 乘法关系的量价拆解，如营业额 = 订单数 × 客单价（派生指标公式可直接提供关系）；用对数分解，各因子贡献相加正好等于总差额 |
| `calendar_adjust` | 天数、星期结构差异的折算 |
| `correlate` | 皮尔逊 / 斯皮尔曼相关系数，附样本量与显著性；样本过少时只给提示，不给结论 |
| `segment_compare` | 分组对比（如高人流低转化与低人流高转化） |
| `describe` / `outliers` | 分布、异常值 |
| `coverage` | 各成员的行数、覆盖日期数与缺失的日期（M8a 实施时增加） |
| `derive` | 用数据集中的值按白名单公式算差、和、比（M8a 实施时增加：避免模型心算派生数字） |

受治理查询的意图在实施时增加了 `time_grain`（按日 / 月分组）与 `compare=custom`（指定对比期，如本期 9 月对比自然月 8 月）。

**探索查询**（第 6 点，分期提供）：`explore_sql(sql, purpose)`。

### 4. 报告与证据核验

报告由一组结论构成。每条结论有类型和引用：

| 类型 | 要求 |
|---|---|
| 事实 | 引用受治理查询的数据集 |
| 计算 | 引用计算工具的数据集 |
| 推断 | 写明依据的数据集与假设 |
| 建议 | 写明前提、预期影响与验证方式 |

`verify` 节点做确定性核验：
- 事实与计算类结论中出现的每个数字，必须能在所引用的数据集中找到（允许按显示精度四舍五入）。
- 找不到的数字标为“未核实”，并在报告中醒目提示，不静默删除。
- 审计后收紧：事实与计算类结论必须引用存在的数据集；正负号必须一致，只有紧跟“下降、减少、负贡献”等词的数字可以对应负值；区间两端都核验；无法解析的数字（大写数字等）为未核实；标题、摘要与“未解释”中的数字对照事实 / 计算类结论引用的数据集同样核验；截断的数据集不能用行数核实总数。
- 只有真实存在的日历日期（完整的 YYYY-MM-DD 或“M 月 D 日”，用日历校验）才当日期排除；09-15、9/10、2026-09 这类短写法按数字核验；阿拉伯数字不看单位一律提取；中文数字（含“零”）表示的数量一律未核实，系统提示要求用阿拉伯数字与完整日期。
- 截断：不限行数、或请求的行数超过系统上限时多取 1 行，据此准确标记截断；截断的数据集会告诉模型；需要全集的计算（差额拆解、覆盖度、相关性、描述统计、分组对比、异常值、求和）拒绝截断的输入，只取单行的计算结果沿依赖继承截断标记。
- 因子拆解中，只有不超过总量最小单位一半（按输入的小数位数）的差视为舍入，其余（输入不一致）单列为“未解释差额”，不归给任何因子；日历折算的两期日期取自数据集的查询窗口。
- 时间段列与维度名、指标显示名都不重名；界面与 PDF 按保存的时间段列画趋势图。
- 字段注释的继承与映射只沿查看者能看到的上游（ADR 0006 的补充）：上游不可见时不沿用其注释、不返回来源，记为 missing；资产详情、注释缺口、问数维度注释、发布检查与分析的 describe_asset 都按当前用户判断。

报告保存为 `analysis_run`，包含计划、步骤、数据集、结论、核验结果、模型与适配器，可以回放和审计。

实施时增加了**修订一轮**：核验发现未核实的数字时，把这些数字逐条反馈给模型，额外给 6 次工具调用。模型可以用计算工具算出、改正引用，或改写为推断。修订后再核验一次，不再继续修订；结果如实记录。

### 5. 变化归因的标准流程

“X 为什么在两个时期差这么多”按以下顺序展开，模型可以跳过不适用的步骤，但要说明理由：

1. **口径与数据是否变了**（Avelis 独有）：
   - 两期之间口径版本是否切换；
   - 来源视图定义、列推导是否变化，有没有受影响与恢复；
   - 采集与新鲜度是否正常，有没有迟到数据。
2. **维度贡献**：差额主要来自哪个区域、门店、类目（`contribution`，按需逐层下钻）。
3. **因子拆解**：有派生或可分解关系时拆成量与价（`factor_decompose`）。
4. **日历因素**：天数、周末、节假日（`calendar_adjust`）。
5. **综合**：按影响大小排序原因，标出证据强弱与仍未解释的差额。

### 6. 探索查询（分期，默认关闭，按数据源开启）

已发布口径覆盖不到的数据（如人流量）需要探索：

- 模型根据血缘与注释写 SQL，走同一套确定性校验：
  - 只能是 SELECT；
  - 表必须是用户可见的已采集资产；
  - 必须有行数上限；
  - 由只读账号执行，并有超时。
- 结果数据集标为**未治理**，报告中引用它的结论自动降级为“推断”。
- 有价值的探索查询可以“转为口径草稿”，进入现有的创建、审批流程。这是推动口径沉淀的入口。
- 注释缺失会直接影响模型能否找到正确的数据，这再次说明了 ADR 0006 的价值。

### 7. 模型数据策略

- `DEFAULT_POLICY` 改为允许：`send_results`、`send_code` 默认 `True`。
- 管理员在模型配置页仍可关闭，页面写明“需保密请接入本地模型（OpenAI 兼容接口）”。
- 关闭时，分析模式不可用，并说明原因，不退化为“看不到数的分析”。
- 分析模式要求模型通过工具调用检测（沿用模型配置页的服务器检测）。
- 安全边界不依赖模型自觉：
  - 权限、可见范围、SQL 校验、预算都是确定性代码；
  - 数据与工具输出中的“指令”一律只当作数据。

### 8. 前端

分析页（也可从问数页进入）包含：
- 计划；
- 步骤时间线：每步的理由、工具、数据集预览；
- 图表：趋势、贡献瀑布、散点、分组对比；
- 报告：结论标注类型与引用，点击可跳到对应数据集与 SQL；
- 未核实的数字醒目标出；
- 运行中逐步推送进度，可以中止。

### 9. 评测

- 计算工具：单元测试，覆盖数值精度与边界（零值、缺失值、样本过少）。
- 演示数据扩充：两个月的合成订单，预埋可知的原因，例如：
  - 某区域一家门店关闭，订单数下降；
  - 某类目促销，客单价下降；
  - 某天采集延迟，数据不完整；
  - 一次口径变更。
- 验收（真实模型）：对“为什么 9 月比 8 月低”这类问题，断言：
  - 报告找出了预埋的原因，且按影响排序；
  - 事实与计算类结论的数字全部通过核验；
  - 每一步查询都经过治理，越权的维度和来源被拒绝；
  - 预算生效。
- 同一问题多次运行，结论的稳定性作为观察指标记录，不作为通过条件。

### 10. 合成电商数据集

- 一套覆盖多个业务域的电商系统表，以及在其上的数仓视图。
- **确定性生成**：脚本加固定随机种子，同一版本生成的数据逐行相同，验收的期望值可以固定。
- 与现有的验收基线库（`shop` / `ads` / `dim`）分开存放、分开灌数。验收模块每次重置演示库时，不重建这套较大的数据。
- 业务域：组织与门店、客流、商品、会员、交易、营销（投放、活动、优惠券）、供应链（仓库、库存、采购）、物流、客服。
- 视图层有明细宽表、日汇总、主题汇总，形成多层列级血缘。
- 大部分列有注释，少数刻意缺失，用来覆盖 ADR 0006 的缺口提示。
- **预埋可知的业务事实**作为评测标准答案，写在生成脚本的场景清单中，不暴露给模型。例如：
  - 门店关闭；
  - 品类促销拉低客单价；
  - 某渠道投放削减带来客流与线上订单下降；
  - 节假日峰值；
  - 客流与商圈、楼层的关系；
  - 一段客流数据缺失。

### 11. 报告导出与定时运行

- **导出**：
  - PDF：结论、图表、证据链附录（SQL、口径版本、数据集摘要）；
  - Markdown；
  - 数据集 CSV。

  导出内容与报告页一致，未核实的数字同样标出。
- **定时运行**：把一次分析保存为“分析任务”（问题、计划模板、时间窗口规则，如“上个自然月对比再上个月”），按 cron 由 worker 定时重跑。
  - 每次运行生成新的报告版本，可与上次对比结论的变化。
  - 以发起人身份运行：每次都重新做权限检查，发起人失去权限后任务自动暂停；执行中被明确拒绝访问所需的口径或来源时同样暂停并通知（不能用“还能看到别的口径”代替）。
  - worker 消费定时 Job 时在任务锁下重新检查任务状态，已暂停的任务跳过、不创建运行。
  - 运行失败或核验发现未核实的数字时，在任务上标出，不静默跳过。
  - 通知渠道先做站内；邮件、IM 之后按需接入。

| 期 | 内容 | 依赖 |
|---|---|---|
| M8a | 合成电商数据集（第 10 点）、分析图、上下文工具、受治理查询数据集、贡献 / 因子 / 日历计算、报告与核验、报告导出与定时运行、数据策略默认允许、分析页；**变化归因**场景验收 | 合成电商数据集 |

| M8c | 探索查询与“转为口径草稿” | M8a |

## 后果

- 分析一次会发起多次查询，产生更多数据库负载与模型费用。预算与缓存是必需的，不是可选项。
- 分析结果具有不确定性：同一问题、同一数据，结论的措辞和侧重可能不同。
  - 数字由核验保证，结构由标准流程约束。
  - 运行记录保留全部步骤，便于复现和审计。
- “相关不等于因果”要体现在报告里：相关只作为线索，建议必须附验证方式。
- 问答模式的行为不变（M6）。数据策略默认值的改变会让问答的解释改为由模型生成，相应的验收断言需要更新。
