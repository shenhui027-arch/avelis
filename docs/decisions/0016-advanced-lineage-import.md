# ADR 0016：批量血缘导入（语法树优先，模型辅助，可追溯的替换）

- 状态：已采纳（2026-11-04 更新）。已在 v1.0.0 实现（PR #48，后续修复 #54、#59、#62）。提议于 2026-11-01。
- 相关：ADR 0004（引擎适配器）、0008（历史留底与哈希链）、0010（业务中立）；M2 导入血缘（`backend/src/avelis/importer/`）

## 背景

用户的问题（2026-11-01）：“导入文件里会有很多 SQL，它会拆出来批量创建血缘吗，这里是先解析出来语法树还是靠大模型完成的……我们需要一个高级完善的血缘导入机制”；随后补充：“还要有大模型识别的能力，比如比较复杂的 Python 脚本文件，里面可能很不规范，规则导入就很可能会出问题”。

M2 的导入已经是“语法树优先”：

- SQL 按分号切分（识别引号与注释），逐条用 sqlglot 按数据源方言解析，结合已采集的表结构算出列级血缘，直接写入 `lineage_edge`（origin=import）；
- 脚本内建的表回填进 schema 供后续语句使用，`USE` 切换默认库，`${param}` 标为待补参数；
- 只有 Python / Shell 中非 SQL 的数据操作交给模型，生成候选边，必须人工确认；发送前脱敏，受“允许发送代码”策略控制。

缺口：

1. 只认 INSERT / INSERT OVERWRITE / CTAS / CREATE VIEW AS；MERGE、UPDATE、Hive 多路 INSERT、物化视图、先写 CTE 再 INSERT、RENAME / SWAP 都不认；
2. 只按分号切分，会切坏 MySQL `DELIMITER $$`、Oracle `/`、T-SQL `GO`、PostgreSQL `$$` 美元引号；
3. 指向临时表的边只打了标记，A→tmp→B 在图上是两段，中间表污染血缘图；
4. 在请求内同步处理，上限 2 MB，几千条语句的脚本撑不住，也没有进度；
5. 一次只能导入一个文件；
6. 同一文件改了内容再导入，旧边不会被替换，过期的边越积越多；
7. sqlglot 解析失败的 SQL 只能显示失败；
8. 不规范的 Python 脚本（SQL 在函数间拼接、包在自定义函数里、来自配置字典、pandas `to_sql` 等）规则抽不全，也没有办法让模型帮忙；
9. 页面不能按状态分组看语句、不能批量处理候选、看不到哪些表名没对上已采集资产。

## 决定

### 1. 总体流程：确定性为主干，模型只出候选

```text
上传（多文件 / zip / 粘贴）
  → 建批次（import_batch）+ 每个文件一个导入（import_job，按来源键分版本）
  → 入队后台任务（job.kind = import），页面轮询进度
  → 阶段一（逐文件，内存中）：切分 → 语法树解析 → 列级数据流
  → 文件按读写依赖排序（见 §5）
  → 阶段二（一个事务）：临时表折叠 → 写语句、边、候选 → 替换上一版的边 → 继承人工决定
  → 阶段三（可选，逐片段）：模型辅助 → 只写候选（pending），不进已确认血缘
```

原则不变：**能用语法树确定的，绝不交给模型；模型给出的一切都是候选，要人确认后才进血缘。** 导入的边仍是设计时血缘，不参与字段推导指纹，不覆盖数据库观察到的定义。

### 2. 切分：按方言分词，客户端分隔符单独处理

切分分两层：

1. **客户端分隔符**（不是 SQL 语法，是命令行工具的约定，按行识别）：MySQL 系 `DELIMITER xx`、T-SQL 独占一行的 `GO`、Oracle SQL*Plus 独占一行的 `/`。哪些引擎认哪种分隔符，由引擎适配器声明（`Engine.script_separators`，ADR 0004 的做法：引擎差异放在适配器后面），不在导入代码里按方言名写分支。
2. **分隔符之间**用 `sqlglot.tokenize(read=方言)` 分词，在顶层 `SEMICOLON` 处切开。分词器已经处理引号、注释、PostgreSQL `$$` 美元引号；`BEGIN … END`、`CASE … END` 计深度，块内分号不切（`BEGIN;` / `BEGIN TRANSACTION` 不算块）。按 token 的字符位置切原文，行号精确。
3. 分词失败（如未闭合的引号）时退回现有的字符切分，并在文件说明里写明“按分号回退切分”。

存储过程、函数、触发器、匿名块整体作为一条语句，状态 `unsupported`（原因“存储过程 / 代码块，本期不展开内部语句”），可以走 §8 的模型辅助。块内 DML 的确定性展开留到后续（变量、游标、控制流要先有设计）。

### 3. 语句覆盖

`statements.parse_statement` 的结果从“一条语句一个目标表”改为“一条语句若干写入”（`writes: list[Write]`，每个写入有目标表、目标列、边、是否临时）。

| 语句 | 处理 |
|---|---|
| INSERT / INSERT OVERWRITE（含列清单、`WITH … INSERT`） | 现有逻辑；sqlglot 把前置 CTE 挂在 Insert 上，解析时并回查询 |
| INSERT … VALUES | 跳过，“没有来源表” |
| CTAS / CREATE VIEW AS / CREATE MATERIALIZED VIEW | 物化视图单列类型 `CREATE MATERIALIZED VIEW` |
| Hive 多路 INSERT、Oracle INSERT ALL（`MultitableInserts`） | 每个分支一个写入，共享 FROM |
| UPDATE … SET … [FROM …] [WHERE …]，SET 中的子查询 | 构造等价查询 `SELECT <各 SET 表达式> FROM <目标> [JOIN/FROM 来源] [WHERE …]` 交给 `parse_query`，输出列按位置对应 SET 的列；WHERE 记为 filter 影响 |
| MERGE | 每个 WHEN 分支构造等价查询（目标 JOIN USING ON 条件），UPDATE SET 与 INSERT VALUES 的表达式按列对应；ON 条件记为 join_key 影响 |
| ALTER TABLE RENAME、RENAME TABLE、ALTER TABLE SWAP | 表的“改名”：新名 ← 旧名，按同名列 value_direct（列未知时表级），`attributes.op = rename / swap`；旧名在脚本状态中消失，参与 §4 折叠。SWAP 两个方向各一组 |
| CREATE TABLE LIKE | 只复制结构：把来源表的列登记为目标表的列，供后续 INSERT 按位置对列；**不写血缘边**（结构相同不等于数据有依赖，写成边会让影响分析误报） |
| DROP TABLE | 不产生边；记入脚本状态，用于判定中间表 |
| DELETE / TRUNCATE / SET / 只读 SELECT | 跳过并说明 |

UPDATE / MERGE 中目标列依赖自身同名列（`SET v = t.v + s.v` 的 `t.v`）的自环边丢弃。

sqlglot 不支持的写法（例如目前把 MySQL `RENAME TABLE` 当作 Command）在 fork（shenhui027-arch/sqlglot）里修并提上游 issue 与 PR，Avelis 里不写绕行；修好之前这类语句如实显示为 `unsupported`。

### 4. 中间表折叠

**中间表**的判定（只看语法事实，不按表名猜，ADR 0010）：

- `CREATE TEMPORARY / TEMP` 建的表；
- 本批次中先被建出、后被 DROP 的表；
- RENAME / SWAP 后旧名消失的表。

折叠在一个批次内进行（跨文件也折叠，因为文件已按依赖排序）：

- 读中间表的边，与“写入中间表的边”按列复合，得到 A→B；多级中间表反复复合直到没有中间表；
- 关系复合规则：取值∘取值 = 取值，等级取较高者（direct < computed < aggregated）；下游是影响类（filter / join_key / group_by）时，上游取值列成为同类影响；上游对中间表的影响（目标列为空）传到下游目标表；任一段是表级则结果表级；
- 原始各段照常写入 `lineage_edge`，但 `status = intermediate`（所有读血缘的地方只认 `active`，因此不进图、不进问数）；折叠出的边是 `active`，`attributes.via` 记中间表，`attributes.hops` 记组成它的各段边 ID，页面可以展开查证；
- 写入中间表、但本批次没有被读过的边，同样只留 `intermediate`。
- `intermediate` 写入后不再变化（历史保护规则不变，lineage_edge 仍只允许 active → superseded）。中间段只用于查证，不能被人工接受、驳回或修改；人工决定作用于折叠后的边。重新导入时只替换上一版的 `active` 边，上一版的中间段随已替换的导入保留。
- 同一条下游语句里复合出的相同边（来源、目标、关系都相同，常见于上游的过滤、分组影响）只保留一条，各条组成路径合并记在 `attributes.paths`。

### 5. 后台任务、规模与多文件

- 复用 `job` 表与 worker：新增 `job.kind = import`，payload 为批次 ID；`?wait=true` 与其他 Job 一样在请求进程内领取执行（测试与小导入用）。
- 阶段一逐语句解析，进度（文件数、语句数、当前文件）每 200 条或每秒写一次批次行（独立短事务）；阶段二在一个事务中写入，要么整批替换成功，要么什么都不变。
- 性能：表结构只建一次；资产按 `catalog.db.name` 一次性查出做字典（不再每条边查一次）；语句和边批量插入。单条语句超过 1 MB 记为失败“语句过大”。
- 上限：单文件 `AVELIS_IMPORT_MAX_BYTES` 默认提到 20 MB；单批总量 `AVELIS_IMPORT_MAX_BATCH_BYTES` 默认 100 MB；zip 最多 2000 个条目，按解压后大小计量（防压缩炸弹），不支持嵌套 zip；不认识的扩展名跳过并列出。
- 多文件排序：阶段一前先对每个文件做一次轻量预扫（只取每条语句写哪些表、读哪些表），文件 F 读了 G 写的表则 G 在前；有环时环内保持上传顺序并在批次说明里写明。文件内部按书写顺序。

**dbt manifest 与调度系统导出（本期只写设计，不实现）**：

- dbt `manifest.json` 每个节点有编译后的 SQL（`compiled_code`）、目标关系（database / schema / alias）与 `depends_on`，相当于现成的“CREATE … AS 编译后 SQL”加依赖顺序，价值高、实现便宜，建议下一期优先做；
- 调度系统导出（DolphinScheduler、Airflow、Azkaban 等）提供任务图、SQL 任务原文、参数与数据源绑定，价值在于“参数自动补齐”和“任务顺序”，但格式多、版本差异大，放在 dbt 之后。
- 两者都实现为“导入源适配器”：输入一个文件，输出若干（来源键、语言、内容、顺序提示、参数）。本期的多文件 / zip 就是第一个适配器，后续格式按同一接口加。

### 6. 重新导入：按来源键替换，留底可追溯

- **来源键**（`import_job.source_key`）：zip 内的相对路径，或文件名；粘贴时就是填写的文件名。同一数据源、同一来源键下，只有一个“当前版本”（`revision` 递增）。
- 同一来源键、内容哈希与当前版本相同 → 幂等，返回原导入；内容哈希与本数据源另一个当前导入相同 → 也视为重复（保留 M2 的幂等语义）。
- 一次上传里**全部**文件都重复 → 返回原批次；只有部分重复 → 重复的文件复用原导入（不新建版本），但在本批中按本批上下文（依赖排序、其他文件建出的表）重新解析，语句状态与边按本批结果更新。
- 迁移回填：旧数据里同一数据源下同名的导入（粘贴时默认文件名相同），最新一条的来源键是文件名，其余在文件名后加 `#` 与导入 ID 前 8 位；全部保持当前版本，不废弃任何旧边。
- 内容变化 → 新版本。阶段二的同一事务里：上一版写入的边全部 `superseded`（记 `superseded_at`），上一版导入记 `status = superseded`、`superseded_by = 新版本`，审计记 `import.revision`（替换了多少边、继承了多少决定）。旧版本的原文、语句、边都保留，可以从新版本一路追到旧版本。
- **人工决定的继承**：按“语句规范化文本的哈希 + 边签名（来源表列、目标表列、关系）”匹配。上一版里被驳回的解析边，新版同一语句同一条边仍驳回；被接受 / 修改的模型候选，新版同一片段原样继承（新写一条边，`attributes.carried_from` 指向旧边）。对不上的人工决定不继承，新版本的统计里列出“上一版有 N 条人工决定因原文变化失效”。
- 同一片段的模型结果按片段哈希复用，重新导入不重复调用模型。
- 补参数后重新解析也走同一套“整批重写 + 继承决定”，不再只改动部分语句（折叠要求整体一致）。

### 7. 语句状态与页面

语句状态：`parsed` 已解析、`partial` 部分解析、`needs_params` 需要参数、`failed` 失败、`unsupported` 不支持、`skipped` 跳过（不产生数据流）；“待确认”是派生分组：该语句有 `pending` 候选。

页面：

- 新导入：多文件 / zip / 粘贴；选数据源；可选“模型辅助”（见 §8，显示将发送的片段数与字符数）；可填“执行 SQL 的自定义函数名”；
- 批次页：进度条（后台运行时轮询）；文件列表（版本号、替换了哪一版）；语句按状态分组，可筛选、可定位原文；
- 候选：按来源（解析 / 模型 / 折叠）筛选，多选后批量接受或驳回（共用一个理由）；修改仍逐条；
- 未对上的表：列出既不是已采集资产、也不是本批次产生的表名，附出现次数与所在语句，提示“先采集或检查库名”。

### 8. 模型辅助识别

模型在三处辅助，都可以在导入时单独开关，都只产生候选：

| 场景 | 发给模型的内容 | 模型返回 | 之后 |
|---|---|---|---|
| 非 SQL 数据操作（现有） | 片段 | 候选边 | 校验后写候选 |
| SQL 解析失败 / 存储过程 | 语句原文 + 解析失败原因 | 候选边 | 校验后写候选 |
| 不规范的 Python / Shell（新） | 文件按顶层函数 / 类分块，每块附文件头部（import、常量、配置字典） | **数据操作清单**：行号、类型（SQL / DataFrame 读写 / 其他）、还原出的 SQL（未知部分写成 `${名字}`）、读表、写表、置信度、理由 | 见下 |

第三种的关键是**模型只负责“找到并还原”，列级血缘仍由语法树算**：

- 还原出的 SQL 交给同一个确定性解析器（同方言、同 schema），算出列级边；这些边因为原文来自模型，落为候选（origin = `model_sql`），页面并排显示原始代码行与还原的 SQL；
- 校验：行号必须在文件内；还原 SQL 里的表名必须在该块原文中出现，或能由块内常量拼出；来源表必须已采集或由本批次产生；不合格的丢弃并记录原因（与现有 `_validate` 同一套）；
- 与规则抽取对照：同一行段规则已抽到且规范化 SQL 相同 → 记“规则与模型一致”，不重复出候选；规则没抽到 → 新候选；同一行段两边不同 → 候选标“与规则结果不一致”，优先复核；
- 自定义执行函数：用户可在导入时填写（如 `run_sql`），规则抽取把它们当作 `execute` 一样处理。模型在清单中识别出的包装函数会在页面上提示“是否加入”，加入后在该数据源下保存，后续导入直接按规则处理——把模型的发现沉淀成确定性规则，越用越少依赖模型（与 ADR 0013 的方向一致，本期只做数据源级的函数名列表）。

安全与费用：

- 发送前脱敏（现有 `redact`）；只有模型配置里允许“发送代码片段”才发真实模型，否则用演示规则并标明；
- 实际发送的内容逐片段记录（页面“发给模型”可看）；代码与注释中的任何指令都只是数据；
- 模型辅助默认关闭（非 SQL 片段保持 M2 现状：按策略自动走候选流程）。开启时页面先显示将发送多少片段、多少字符；批次上限（默认 200 片段、200 万字符）超出部分不发送并说明；
- 模型调用在 worker 中进行，失败只记录在片段上，不影响确定性结果。

## 数据变更（迁移 0016）

- 新表 `import_batch`：数据源、默认库、状态（queued / running / needs_params / needs_review / done / failed）、进度、统计、选项（模型辅助、自定义函数名）、Job ID、创建人、时间、错误；
- `import_job`：加 `batch_id`、`source_key`、`revision`、`superseded_by`；状态加 `superseded`、`failed`；去掉 `(datasource_id, content_hash)` 唯一约束，改为“同一数据源同一来源键只有一个非 superseded 版本”的部分唯一索引；
- `extracted_statement`：加 `text_hash`（规范化文本哈希，用于继承决定与复用模型结果）、`writes`（JSON，多目标）；加 `(job_id, status)` 索引；
- `candidate_edge`：origin 加 `model_sql`、`folded`；
- `lineage_edge`：status 加 `intermediate`（无结构变化）；
- 数据源级设置“自定义执行函数名”存在 `datasource.options` 之外的导入设置里（`app_setting`，键按数据源）；
- 回填：每个已有导入建一个批次，`source_key = filename`，`revision = 1`。

## 取舍

- **为什么不让模型直接出血缘**：模型对列级对应、聚合等级、过滤与关联的判断不稳定，也无法复现；语法树结果可复现、可解释、零费用。模型的长处是“在乱代码里找到 SQL 在哪、拼出来是什么”，所以让它做这一步，列级仍交给解析器。
- **为什么折叠时保留中间段**：折叠后的边是推出来的，必须能查证；中间段 `intermediate` 不进图，又随时可展开。
- **为什么阶段二用一个事务**：替换上一版与写入新版必须原子，否则中途失败会留下“旧边没了、新边不全”的血缘。代价是大批次的写入事务较长；几千条语句、几万条边在 PostgreSQL 上可接受。
- **为什么 LIKE 不写边**：见 §3。
- **不做的**：存储过程内部展开、跨批次折叠、dbt / 调度系统导入、按表名模式猜中间表、导入来源的“停用”（整体撤销某来源的边）——都留到后续，需要时另起设计。

## 验证
