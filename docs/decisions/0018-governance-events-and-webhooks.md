# ADR 0018：治理事件（含失败事件）与 Webhook 订阅

- 状态：草稿（2026-11-01）；2026-11-02 定为 1.1 第三项（在口径语义提示、MCP 服务之后），实施前定稿“待讨论”各条。
- 相关：ADR 0008（历史留底与哈希链）；后台任务 `jobs.py`；参考 Apache Gravitino 的事件监听框架（每个操作都发前置、成功、失败三段事件）

## 背景

现在的审计是 `audit.record(...)`：77 处调用，和业务写入在同一事务里提交，只追加，受哈希链保护。它存在三个缺口：

1. **只记成功。** 事务回滚时审计也跟着回滚，所以“谁试图发布口径但校验失败”“导入失败”“采集连不上”在审计里看不到。失败只能从 `job` 表或日志里找。
2. **没有对外通知。** 口径进入 `affected`（受影响）、采集发现结构变化、血缘导入失败，企业都希望推到自己的 IM 或告警系统。现在只能人上页面看。
3. **事件名不统一。** `action` 是自由字符串，外部系统没有稳定的契约可依赖。

Gravitino 的做法是：每个操作都有前置、成功、失败三个事件，通过监听器统一分发，订阅方不影响主流程。

## 决定

### 1. 事件契约

```text
GovernanceEvent
  id          稳定 ID（订阅方用来去重）
  type        <对象>.<动作>，例如 metric_version.published、collect.failed
  outcome     success | failure
  at          UTC 时间
  actor       {id, name} 或 system
  object      {type, id, name?}
  detail      结构化内容，沿用审计的约束：不得含口令、令牌、SQL 原文、数据行
  error?      失败时的错误码与简短原因（已脱敏）
```

- `type` 是一张有限的枚举表，写进文档，新增只追加不改名。
- 不做“前置事件”。Avelis 没有需要拦截操作的扩展点，前置事件只会增加噪音。

### 2. 失败事件独立提交

- 成功事件：仍在业务事务里写 `audit_event`，和现在一样。
- 失败事件：业务事务回滚后，用**单独的短事务**写一条 `outcome = failure` 的审计。它同样进入哈希链。
- 只对写操作和后台任务记录失败；查询类操作的失败不记，避免审计膨胀。

### 3. 对外投递用发件箱，不在请求里直接调外部

- 写审计的同一事务里，按订阅规则写一条 `event_outbox`。
- worker 读取发件箱并投递，至少投递一次，订阅方按事件 `id` 去重。
- 退避重试；超过上限标为 `dead`，在页面上可见、可重投。
- 投递失败不影响业务操作，也不回滚审计。

### 4. Webhook 订阅

- 管理员配置：URL、订阅的事件类型、签名密钥。签名用 HMAC-SHA256，放在请求头里，密钥加密存储（与数据源口令相同的方式）。
- 请求体只含事件契约里的字段。订阅不放宽任何权限：`detail` 里不会出现订阅者本来看不到的信息。
- URL 只允许 http/https。可配置禁止内网地址，防止 SSRF。

### 5. 首批事件类型

口径的提交、发布、驳回、受影响、失效；关联路径的批准、受影响；采集的完成、失败、结构变化；血缘导入的完成、失败；变更归因的“不可用”（权限不足或审计未开启）；登录失败次数超过阈值。

## 不做

- 不做插件式监听器（在进程内加载第三方代码）。对外只通过 Webhook。
- 不保证事件顺序。需要顺序的订阅方按 `at` 和对象版本自行处理。
- 不推送数据行或查询结果。

## 后果

- 好处：失败可审计、可告警；企业能把治理流程接进现有系统；事件名成为稳定的对外契约。
- 代价：新增 `event_outbox`、`webhook_subscription` 两张表和一个迁移，worker 增加投递循环，还要维护事件类型表。
- 风险：失败事件的写入路径和业务事务分开，要测试“业务回滚、失败事件写入”与“两者都失败”的情况。

## 待讨论

1. 失败事件是否也给普通用户看，还是只给管理员？
2. 首批是否需要企业微信、钉钉、飞书的消息格式适配，还是先只做通用 JSON？
