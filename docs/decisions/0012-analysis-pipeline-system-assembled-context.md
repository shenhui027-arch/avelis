# ADR 0012：分析流程改为“系统组装上下文、模型少轮推理”

- 状态：已采纳（用户要求，2026-10-30：“太慢了……请你先优化工具调用”“为啥任务被切的这么细，架构设计到底哪里不合理”）
- 日期：2026-10-30
- 取代：ADR 0007 第 2 点的分析图（计划 → 执行循环 → 核验）与第 5 点“由模型按顺序排查”的执行方式；ADR 0011 第 10 点提前到 PR #10 实施

## 背景：实测与原因

实测（`.demo/eval/20261030-192729.json`，52 次运行）：单次分析中位 106 秒，工具执行合计中位 9.4 秒，其余约 95 秒是模型推理与往返；每次运行中位 24 个步骤。

慢的原因不是上下文不够大（DeepSeek 的上下文足够放下一个问题需要的全部相关信息），而是架构把任务切得过细：

1. **模型当检索器**：每次运行从空白开始，模型要自己调用 `search_metrics`、`describe_metric`、`describe_asset` 找口径、读维度，一次一轮。
2. **模型当流程调度器**：“为什么变化”的排查顺序是固定的（变更 → 数据健康 → 维度贡献 → 因子 → 日历），系统提示却要求模型逐个调用 `changes`、`data_health`、`explain_change`、`calendar_adjust`，每个都多一轮推理。
3. **强制的计划轮**：第一轮必须单独调用 `submit_plan`，最多 6 轮，计划本身不产生任何数据。
4. **上下文越滚越长、缓存失效**：每轮都把完整历史（包括冗长的工具 JSON）重新发给模型；系统提示第 2 行就插入了日期、窗口、预算等动态内容，前缀缓存几乎无法命中。

确定性的检索和固定流程应由系统完成，模型只负责理解问题、判断要不要深挖，以及写出结论。这与 ADR 0009 第 7 点“判断交给确定性引擎”是同一个原则。

## 决定

分析运行改为四段：

1. **理解**（1 次模型调用，结构化输出）：
   - 系统先按问题文字从当前用户可见的口径中检索候选（前 10 个，含名称、别名、维度、单位），连同窗口一起交给模型。
   - 模型只输出 `scope`：问题类型（变化 / 关系 / 其他）、指标编码、筛选条件、窗口；无法确定时输出追问。
   - 候选检索在 ADR 0011 第 1 点完成前先用现有的关键词匹配，排序后截断。
2. **系统预检**（确定性，不经模型）：
   - 变化类问题：按 `scope` 一次执行 `describe_metric`、`changes`、`data_health`、`explain_change`（含筛选与自动因子拆解）、`calendar_adjust`，产出带编号的数据集。
   - 关系类问题：按 `scope` 取多指标、同维度的数据，并计算相关与分组对比。
   - 产出一份紧凑的**上下文包**：每个数据集的编号、标题、关键汇总、前若干行，按 token 设上限。完整数据保存在数据集中，不进入上下文。
   - 预检中的查询照常计入查询额度、检查权限，并记录步骤。
3. **推理**（模型，通常 1–3 轮）：
   - 模型读上下文包，可以直接提交报告，也可以发起有针对性的下钻（`query_metric`、`query_sql`、`contribution` 等）。
   - 允许一轮发出多个互不依赖的工具调用。
   - 不再有单独的计划轮：报告里增加可选的“分析方法”说明，替代 `submit_plan`。
4. **核验与修订**：沿用 ADR 0009；修订仍然只有一轮。

**提示与上下文**：
- 系统提示只放稳定内容（规则、工具说明、写法示例），放在最前面，以便模型服务的前缀缓存命中。日期、窗口、预算、上下文包等动态内容放在随后的用户消息里。
- 工具返回值统一紧凑化：汇总加有限行预览，按 token 设上限；被截断时注明。

**模型与思考强度可配置**（用户要求，2026-10-30）：
- 模型设置页的每个用途（问数理解、导入解析、分析）除了选模型，还可以选**思考强度**：关闭 / 低 / 中 / 高 / 最高。默认是“中”。
- 选项按提供方的能力显示，只显示该模型支持的档位；提供方会把某个档位映射成另一档时（例如某档实际按“高”执行），在界面上注明实际生效的档位。映射关系以提供方官方文档为准，并用一次真实调用记录到的推理 token 数核实。
- 请求参数按提供方适配：OpenAI 兼容接口使用 `reasoning_effort`；需要单独关闭思考的提供方（如 DeepSeek）按其文档传关闭参数。开启思考并且使用工具调用时，按提供方要求在后续请求中带回推理内容（DeepSeek 要求带回 `reasoning_content`，否则返回 400）。
- 每次运行的记录里保存当次实际使用的模型与思考强度，评测汇总按这两项分组，便于比较速度与准确性。
- 实现与实测（2026-10-30，DeepSeek `deepseek-flash`，以[官方文档](https://api-docs.deepseek.com/guides/thinking_mode/)为准）：
  - 参数在 `modelcfg.build_chat_model` 集中适配：“关闭”传 `extra_body={"thinking": {"type": "disabled"}}`；其余档位传 `reasoning_effort`。文档只有 low / high / max，“中”按“高”执行，页面注明。没有核实过的提供方不显示档位、不传思考参数。
  - 默认档位在 `modelcfg.DEFAULT_EFFORT` 一处配置（当前各用途为“中”）；按阶段固定的参数由系统决定，不在页面开放（例如理解阶段关闭思考、限制输出长度）。
  - 实测推理 token（同一请求各 3 次）：关闭时为 0；低 3942–7946、中 3741–7979、高 3665–6389，三档相近；最高 9149–12128，明显更多。
  - 开启思考并使用工具调用的三轮真实请求，不带回 `reasoning_content` 也没有返回 400（默认档位与 `reasoning_effort=high` 各一次）。langchain_openai 不保留 `reasoning_content`，目前不在适配层带回；提供方改为强制时再补。
  - 思考开启时 temperature 不生效，不依赖它。

**度量**：
- 每次模型调用记录耗时、输入 / 输出 / 缓存命中的 token 数，以及本轮发出的工具调用数，存进运行步骤。
- 评测汇总新增：每次运行的模型轮数与总耗时的中位数和 P90。
- 目标：变化类问题中位不超过 40 秒，模型调用中位不超过 5 次。准确性门禁不变。

## 不变

- 数字按引用渲染与结构核验（ADR 0009）、探索查询的校验（ADR 0009 第 6 点）、权限与预算、审计，都不变。
- 模型仍然可以调用全部工具，只是不必为固定流程逐个调用。

## 后果

- 常见问题从约 24 步降到少数几次模型调用，响应时间主要取决于预检的查询耗时与 1–3 轮推理。
- 系统预检固定了“为什么变化”的排查范围；需要预检之外的分析时，模型仍可下钻。预检本身的覆盖面由评测衡量。
- `submit_plan` 与 `PLAN_ROUNDS` 删除；回放轨迹需要重新录制。
