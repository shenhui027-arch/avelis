## 1. 定位与第一阶段成功标准

Avelis 是建立在数据库血缘、业务口径和变更管理之上的智能问数平台。每个答案都要有来源、口径、版本和权限依据；上游变化后，系统知道哪些答案需要重新确认。首期面向 StarRocks。

**第一阶段成功标准**：Avelis 能感知一次真实的视图定义变化，由后端阻止受影响的旧口径继续被使用，并通过可追溯的复核流程恢复正确问数。

- 本地镜像：`starrocks/allin1-ubuntu:3.5.14`、`postgres:18-alpine`、`mysql:8.4.10`。
- 真实模型：2026-10-29 起使用用户提供的 DeepSeek 测试密钥（只在本地 `.env`），`deepseek-flash` 端到端已验证；Anthropic 未验证。

- SQLGlot 30.25.0，`starrocks` 方言实测：
  - 规范化指纹能区分“只改格式”和“改了定义”；
  - `SUM(paid_amount)` 与 `SUM(paid_amount - refund_amount)` 的值血缘正确；
  - 自写语法树遍历能分出取值、过滤、分组、JOIN 键四类列引用；
  - CTE、FROM 子查询、窗口、JOIN、UNNEST、建表与物化视图 DDL 可解析；
  - `SELECT … INTO OUTFILE` 解析失败 → 守卫必须“解析不了就拒绝”；多语句可识别；未知列 `qualify` 报错。
- StarRocks 3.5.14 实机核验已在 M0 完成，20 条结论与对设计的影响见 [starrocks-notes.md](starrocks-notes.md)。对 M1 影响最大的几条：视图定义里的别名列带库名前缀，解析前要归一化；视图与外部表在 `tables_config` 中没有 ID；删除被视图引用的列不会被 StarRocks 阻止；视图是 `SECURITY NONE`，授予视图等于暴露其来源；旧式 `ENGINE=mysql` 外部表连不上 MySQL 8.4 默认认证。

## 4. v0.1 范围

### 做

1. **采集**
   - StarRocks 连接器（真实）：表、字段、类型、视图定义、表模型与键、外部 Catalog 的类型和连接地址（不读口令）。
   - MySQL 元数据连接器（真实，只读 `information_schema`）：用于把 StarRocks 外部表追到 MySQL 真实表。
   - 测试用 `FakeConnector`，界面和数据中标“测试适配器”；演示数据只放在本地独立容器。
   - 演示数据是一套电商表：事实表（订单、订单明细、退款明细）在 StarRocks，维表（客户、商品、类目、区域）在 MySQL；StarRocks 通过 JDBC Catalog 和 `ENGINE=mysql` 外部表两种方式访问维表。
2. **血缘**：列级，区分取值（直接 / 计算 / 聚合）与影响（过滤 / JOIN 键 / 分组）；视图套视图、CTE、等值 JOIN、FROM 子查询；外部表身份映射（端点 + 库表 + 列）；多业务域串联。
3. **导入血缘（新增）**：上传 SQL 文件、粘贴 SQL、上传代码，AI 辅助识别数据流，人可以接受、驳回、修改。详见第 6 节。
4. **粒度（新增）**：粒度是资产版本的一等属性；JOIN 标基数；发布指标与生成查询时检查放大。详见第 7 节。
5. **口径与治理**：指标及版本、业务域、负责人、一致性维度、跨域关联路径；状态机；禁止自审；变更 → 影响 → 复核 → 发布。
6. **受约束问数**：模型只输出结构化意图，SQL 由已发布指标确定性编译、校验、只读执行；答案依据与审计。
7. **工作台界面**：按 Avelis UI 设计系统和原型实现 5 个导航区（工作台、血缘、目录、变更、问数）+ 导入页 + 设置。

### 不做（v0.1）

多数据库类型的完整支持（MySQL 只做元数据）、Hive / Iceberg Catalog 接入（只显示“未接入”占位）、调度系统血缘、UNION 等集合运算的列级血缘、Java / Scala 代码的确定性解析（只走模型候选）、行级权限、SSO、数据快照与历史重算、图数据库、消息队列、多 Agent 编排。

## 5. 关键设计决定

1. **模型只出意图，不写可执行 SQL**。问数 SQL 由已发布指标版本确定性编译（SQLGlot 构建）并校验。
2. **四层数据模型**：身份层（稳定 ID，与名称分离）→ 观察层（采集批次、资产版本、字段版本、定义，只追加）→ 推导层（解析结果、列级血缘边，带解析器版本，可重算）→ 治理层（人工确认、指标版本、关联路径、复核，只追加）。上层只引用下层的具体版本。
3. **人工确认绑定“字段推导指纹”**（上游字段版本 + 表达式哈希）：指纹不变才沿用，指纹变化即失效。
4. **按列判断影响，证据不全按受影响处理**；外部表匹配为“候选”时，影响判定按“可能受影响”。
5. **外部表**：在血缘中自动接到他库真实表（同一张表），不设单独匹配页面；只按“端点（含别名）+ 库表 + 列结构”匹配，不按名称相似。
6. **跨域查数只走两域负责人都批准的关联路径**，并在一致性维度上先各自聚合再关联。
7. **模型产出一律是候选**：导入血缘的模型边、问数的意图，都不能绕过确定性校验；模型边必须人确认后才计入“已确认血缘”。
8. **凭据与数据外发**：数据源口令加密存储、不回传、不进日志、不进模型上下文；发给模型的内容可配置，默认只发元数据；代码发给模型前先做密钥脱敏，并在界面上显示将发送的片段。
9. **前端不用 antd**：按 Avelis UI 自建组件（必要时用无样式交互原语），血缘图用 @xyflow/react；样式全部来自设计令牌。
10. **发现延迟**：轮询采集（默认 15 分钟，可手动触发），变更记录可确认的生效区间；界面写明“未发现变更 ≠ 没有变更”。
11. **（已由 ADR 0003 取代：元数据库只支持 PostgreSQL）** 原决定：元数据库同时兼容 PostgreSQL 与 MySQL：SQLAlchemy 2 + Alembic，只用两者共有的能力（通用 JSON 类型、不用数组与部分索引、不依赖 `RETURNING`、血缘遍历用两者都支持的递归 CTE、时间统一存 UTC）。CI 在 PostgreSQL 18 与 MySQL 8.4 上各跑一遍迁移与测试；演示环境两种都提供。
12. **引入 Redis（协议兼容，演示用 Valkey 8）**：用于后台任务队列（采集、导入解析、模型调用、粒度核验查询）、答案缓存（键含指标版本、资产版本、权限范围、新鲜度）、采集互斥锁、令牌吊销与限流。Redis 不是事实来源：任务状态与结果落元数据库，Redis 丢失只影响性能和重试。
13. **前后端分离**：`backend/`（FastAPI，REST + OpenAPI）与 `frontend/`（React SPA）独立构建、独立容器；前端只通过 `/api` 访问后端，类型从 OpenAPI 生成；认证用后端签发的短期访问令牌（可在 Redis 吊销），CORS 只允许配置的前端来源。

## 6. 导入血缘（SQL 文件、粘贴 SQL、代码）

### 流程

```
来源（文件 / 粘贴 / 代码）
  → 抽取：找出 SQL 语句与非 SQL 的数据操作
  → 确定性解析：SQLGlot 语法树 → 语句级数据流（目标表 ← 来源表）→ 列级边
  → 模型推断：只针对确定性解析覆盖不到的片段，产出候选边（带代码行号与置信度）
  → 人工处理：接受 / 驳回 / 修改 / 补参数 / 手工补边
  → 提交：写入血缘（来源分别记为“解析”“人工”），候选的处理结果单独留痕
```

### 识别能力分层

| 输入 | v0.1 做法 | 结果类型 |
|---|---|---|
| `.sql` 文件、粘贴的 SQL（多语句脚本） | SQLGlot 解析；按语句顺序串联临时表与中间表；`INSERT … SELECT`、`CREATE TABLE/VIEW … AS SELECT`、`INSERT OVERWRITE` | 解析边，直接写入（可修改） |
| Python 中的内嵌 SQL（`spark.sql`、`cursor.execute`、SQLAlchemy `text`） | Python `ast` 抽出字符串字面量（含三引号、简单拼接），再走 SQL 解析 | 解析边 |
| Shell 中的内嵌 SQL（heredoc、`-e "…"`） | 规则抽取后走 SQL 解析 | 解析边 |
| PySpark DataFrame 链式调用、pandas 等 | 模型推断 | 候选边，必须人确认 |
| 动态 SQL（表名、列名来自变量或模板） | 不猜测；提示补参数（如 `${dt}`、`{table}` 的取值）后重新解析 | 未识别 → 补参数后成为解析边 |
| Java / Scala 代码 | 只走模型推断 | 候选边 |

### 数据模型补充

- `import_job`：来源类型、文件名、语言、方言、默认库、提交人、状态、时间。
- `import_source`：原文（加密存储可选）、内容哈希（同一内容重复导入幂等）。
- `extracted_statement`：行号范围、抽取方式（解析 / 模型 / 未识别）、语句类型、目标表、解析状态与未支持原因。
- `candidate_edge`：来源列 → 目标列、关系类型、来源（解析 / 模型）、置信度、证据行号、处理结果（接受 / 驳回 / 修改）、处理人、理由。
- 写入后的边沿用现有 `lineage_edge`，来源记为“解析”或“人工”，证据指向 `import_job` 与行号。

### 边界

- 模型推断的准确率不作承诺；没有模型 key 时用演示适配器，界面标“演示模型”。
- 发给模型前做密钥脱敏（连接串、口令、令牌模式），只发确定性解析覆盖不到的片段。
- 导入的血缘属于“设计时血缘”，与数据库观察到的定义并存；两者冲突时在变更页提示，不自动覆盖。

## 7. 粒度

### 为什么关键

主表一行一个订单（或一片晶圆），raw 表一行一笔退款（或一次扫描）。直接按 id 关联是 1:N，对主表金额求和会重复计数。列级血缘只说明“值从哪来”，看不出这种放大，所以粒度必须单独建模。

### 粒度从哪来

| 来源 | 例子 | 记为 |
|---|---|---|
| 数据库观察 | StarRocks Primary Key / Unique Key / Aggregate Key 表的键；MySQL 主键与唯一索引 | 观察 |
| SQL 解析 | 视图的 `GROUP BY` 键；`SELECT DISTINCT` 的列 | 解析 |
| 人工声明 | Duplicate Key 表、外部表、导入的代码产物 | 人工 |

每个粒度都可用只读查询核验唯一性（`GROUP BY 键 HAVING COUNT(*) > 1 LIMIT 1`，带超时），记录核验时间与结果；超时记为“未核验”。

### 传播与基数规则（v0.1 子集）

- 聚合：输出粒度 = 分组键。
- JOIN：若右侧按其粒度键关联 → N:1，输出粒度保持左侧；否则 → 1:N 或 N:N，输出粒度未知，标记“可能放大”。
- `UNION`、窗口函数之外的复杂情形：粒度未知，需人工声明。
- 关联基数写在 JOIN 边和跨域关联路径上，并可用核验查询确认。

### 在哪里生效

- 血缘图：节点显示粒度与核验状态；JOIN 边显示基数，`1:N` 用警告色。
- 指标发布检查：可加度量（SUM、COUNT）若在 1:N 关联之后聚合，阻止发布并提示先聚合。
- 问数编译：不同粒度的指标先各自聚合到共同粒度（一致性维度），再关联。
- 变更：粒度变化（键增删、表模型变化）作为语义变化进入影响分析。

## 9. 验收故事

故事 1–7 按原需求（daily_sales 300 → 定义改为净额 270 → 拦截 → 复核 → 发布新口径 → 删除依赖字段的异常场景）。新增：

- **故事 8 导入血缘**：导入 `etl_orders.sql`（多语句）和 `etl_daily_orders.py`（内嵌 SQL + DataFrame + 动态 SQL）。断言：解析边写入且带行号证据；2 条模型候选在确认前不出现在“已确认”血缘中；驳回 1 条、接受 1 条、修改 1 条后数据库状态正确；动态 SQL 补参数后能解析；同一文件重复导入不产生重复边；没有模型 key 时候选来自演示适配器并有标记。
- **故事 9 粒度与放大**：`shop.orders`（粒度 `order_id`）直接关联 `shop.order_items`（粒度 `order_item_id`，订单 1001 有两行）或 `shop.refund_raw`（粒度 `refund_id`）后对 `paid_amount` 求和，StarRocks 实际返回 400，而正确值是 300。断言：系统识别 1:N、阻止该指标发布并给出原因；改为先聚合再关联后通过，结果为 300。跨域场景：交易域的订单明细与商品域的商品维表（MySQL，经外部表）按 `product_id` 关联是 N:1，可以通过；类目销售按明细金额求和而不是订单金额。

## 11. 已知边界

- StarRocks 结论只来自本机 Docker 3.5.14 单节点；多 FE/BE、存算分离、其他版本、生产权限体系待验证。不连接任何生产库。
- 真实模型端到端（问数意图、导入候选）在拿到 key 前标“未验证”。
- 可追溯 ≠ 可复现：保存 SQL、口径与元数据版本，不保存数据快照。
- 轮询发现有延迟，最长等于采集间隔。
- 未归属业务域的资产默认只对管理员与维护者可见（`AVELIS_UNASSIGNED_ASSET_POLICY`）。
- 引擎能力只声明真实联调过的：MySQL 目前只采元数据并作为外部表的追溯目标。
